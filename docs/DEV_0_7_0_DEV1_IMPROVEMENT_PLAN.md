# 0.7.0.dev1 改进方案：托管 Run、执行生命周期与执行授权

本文保留 2026-09-28 的设计基线和实施进度，完整托管 Run 方案仍未验收。
后续 `0.7.0.dev2` 已实现活动观测、继承期限、有界父子调用与托管停滞 handler，
这些能力不等于本方案的同 Run 修订或可信授权闭环。用法见
[执行观测指南](EXECUTION_OBSERVABILITY.md)，当前证据见
[验收记录](EXECUTION_OBSERVABILITY_ACCEPTANCE.md)。

日期：2026-09-28。分支：`release/0.7.0dev1`。
核查基线：`b85b828487548cbac5f6ce6adfd2d4ab3ed46eae`，包版本仍为 `0.7.0.dev0`。

**状态：方案已获准实施；下述新增能力尚未通过验收。** 用户确认保留现有公开 API，
并保留历史数据库的升级路径。本文中的新接口、字段及模块名是设计目标；实现、验证与剩余限制
须另行记录，不能仅凭本文认定其已可调用。

## 1. 目标与职责

让应用能够创建多任务 Run、观察执行、暂停、修改 handler 或输入、预览影响并在同一 Run 中继续。
SDK 承担执行生命周期、执行权限及恢复事务的协调；应用保留业务决策、用户认证和业务授权。
开发调试与正式运行使用相同的持久化机制，不能靠重建 Run、清空历史或重置预算完成恢复。

| 责任 | SDK 承担 | 应用或适配器提供 |
| --- | --- | --- |
| 流程执行 | 调度、领取、租约、心跳、超时、嵌套等待、取消、清理、结果交接与恢复 | handler、依赖关系、业务路由及结果可接受条件 |
| 执行授权 | 把已获许可的操作绑定到 Run/task/attempt/generation，检查、委托、收窄及撤销权限 | 认证后的主体、租户边界、业务许可策略及策略版本 |
| 修订与复用 | 根据声明计算影响范围，隔离旧执行，持久化并恢复修订事务 | 产物关系、兼容条件、业务有效性和外部操作是否可重试的证据 |
| 预算 | 累计 SDK 管理的执行额度、预留与结算、截止时间及追加记录 | token、费用、业务派发等计量及相应限制 |
| 诊断 | 谁在等待谁、未结算步骤、实际部署、缺失证据与执行历史 | 最后代码变化、最后业务验证、验收范围与业务进度 |

ModPort 的编译、Minecraft 启动、harness 契约正确性和 planner 决策仍属于应用。
SDK 可以承载其声明和证据，不据此推断游戏已启动或业务已验收。
本方案不增加远程控制服务、跨机器自动接管或新的数据库后端。

## 2. 现状证据与缺口

以下结论来自上述基线的源码核查。附件中的 `opencode_cleanup_unconfirmed` 是下游问题线索，
本轮未复现该错误，也未证明其根因位于 SDK；需在后续适配器真实路径中验证。

| 问题 | 已有能力与证据 | 需要补齐的部分 |
| --- | --- | --- |
| 应用拼装多任务生命周期 | [`Dispatcher`](../src/dispatcher_sdk/application.py#L93) 已拥有 Host、Runtime 和 inbox；[`submit`](../src/dispatcher_sdk/application.py#L175) 创建单任务 Run；[`Orchestrator`](../src/dispatcher_sdk/orchestrator/engine.py#L175) 支持多任务 | 统一的多任务托管接口，以及不依赖业务 handler 导入的检查和控制入口 |
| 缺少持久化暂停 | [`RunState`](../src/dispatcher_sdk/orchestrator/types.py#L10) 只有运行和终态；[`wait`](../src/dispatcher_sdk/orchestrator/reducer.py#L72) 是普通等待记录；[`claim_predicate`](../src/dispatcher_sdk/execution_kernel/claiming.py#L5) 没有按 Run 暂停的约束 | 调度与 Kernel 领取共同执行的持久化控制，以及明确的暂停完成判据 |
| 正常运行中难以修改再继续 | 普通操作已有 revision CAS；[`reopen_run`](../src/dispatcher_sdk/orchestrator/recovery.py#L465) 有持久化恢复事务，但只允许已失败或取消且满足结算条件的 Run | 面向已暂停 Run 的修订预览、失效传播、新部署激活和崩溃恢复 |
| 执行权限缺少统一入口 | [`HandlerEffects`](../src/dispatcher_sdk/execution_kernel/context.py#L12) 检查活动租约和 fence；恢复记录接受调用方提供的 actor、来源和授权对象 | 从可信授权上下文到实际执行的持续检查，覆盖委托、工具调用和恢复；字段或摘要不能充当身份认证 |
| 结果与清理缺少统一呈现 | [sandbox](SANDBOX_RUNTIME.md) 已保留收集输出并支持只恢复 disposal；[请求收据](REQUEST_RESULT_RECEIPTS.md) 已分开记录结果、传输和 ACK | 将这些能力接入托管收尾流程，保留结果候选、原始错误和清理义务，避免不必要的重跑 |
| 恢复不等于预算连续 | Kernel 已执行每条命令的机械重试上限；[`_validate_decision`](../src/dispatcher_sdk/orchestrator/recovery.py#L297) 对预算变更主要检查理由字段 | 按 Run 跨 attempt/generation 的累计额度、外部计量预留及绝对截止 |
| 有查询原语，缺少直接可用的运行说明 | [`get_run_summary`、`get_task`、`list_tasks`](../src/dispatcher_sdk/orchestrator/runs.py)、[`read_events`](../src/dispatcher_sdk/orchestrator/engine.py#L330)、[可执行性和取消检查](SDK_DIAGNOSTICS_AND_PROJECTIONS.md) 已存在 | 组合成有界诊断；明确观测完整性、跨库一致性及下一项待处理义务 |

不能把已有的租约、通知、恢复记录和 sandbox 清理机制当成空白重写。
本轮主要补足其间的协调协议，并让普通应用通过托管接口使用。

## 3. 兼容策略

1. 保留 `Dispatcher.submit()`、`Task.wait()`、`Orchestrator`、`Runtime`、既有收据及恢复 API。
   现有单任务、重试、回调投递、终态和显式业务验收语义不变。
2. 通过新建的托管多任务入口启用新控制协议。既有 Run 不在普通打开时自动加入；
   如需接管，执行显式的检查、登记与迁移，并确认执行、资源和部署状态。
3. 保留原 `RunState` 和旧快照契约。新接口另返回 `control_state`，例如 `active`、
   `pausing`、`paused`，以及独立的 `recovery_obligations`；旧接口中的 `running`
   不能被新控制层解释为一定可领取。界面和诊断应同时展示两者。
4. 保留命令及结果 V2 的原有含义。新增控制元数据采用显式关联记录或新接口类型；
   不给历史命令补写新的授权证明，不以原地修改 payload 的方式迁移。
5. 如需 schema 变化，提供显式的复制升级、校验和激活路径；普通构造和状态查询不执行 DDL。
   升级保留 Run、attempt、generation、收据、预算及未决外部效果。
   新库必须让不支持该控制协议的旧 SDK writer 拒绝写入，不能让旧 worker 绕过暂停。
6. 已登记托管的 Run 在底层执行入口仍须遵守控制规则，不能经 `.runtime`、`.orchestrator`
   绕过。旧低层接口可继续操作未登记的原有 Run；对新托管 Run，缺少必要上下文时应明确拒绝。
   这项新增限制只作用于主动采用新协议的 Run，需在迁移文档中说明。

复制数据库不是执行授权。存在旧进程或旧数据库写入源时，必须先证明其停止或被隔离，
再激活新库；继续使用现有[存储升级](STORAGE_AND_UPGRADES.md)与[本地激活](LOCAL_RECOVERY.md)边界。

## 4. 具体改进措施

### M1：统一托管 Run 与独立控制入口（P0）

拟议新增 `Dispatcher.create_run(spec, request_id=...) -> ManagedRun`，
并提供 `run(run_id)` 恢复句柄。`RunSpec` 描述任务、依赖、handler 绑定、业务路由规则、
授权范围和预算。创建 Run 的请求幂等；相同请求内容返回原记录，不同内容返回冲突。

`ManagedRun` 拟提供 `snapshot`、`pause`、`preview_revision`、`revise`、`resume`、
`cancel` 和 `inspect`。调用方保留稳定请求 ID；revision/generation 的读取、CAS 和重复命令
处理由托管层完成。发生竞争时重新检查，不能把过期预览自动套到新状态上。

SDK 根据应用声明的条件调度多任务；任务终态不等于业务通过。现有底层 dispatch 只要求前置
attempt 已结算，托管层不能悄悄将其改成“任意终态都允许业务继续”，也不能擅自发明业务路由。

拟议新增 `RunController.open(path, ...)`，不导入业务 handler、不启动 worker：

- 只读入口可查看摘要、历史绑定、控制状态和恢复义务。缺少部署时报告缺失信息。
- 写入口只执行已认证、获授权的控制命令；提交暂停、取消、修订意图不要求能导入业务代码。
- 准备修订可以引用尚未安装的目标部署；激活和重新派发必须验证匹配的新 worker。
  准备成功不能被显示为部署可用或恢复完成。
- 读取、授权策略服务或恢复适配器不可用时分别说明影响；不能借导入失败绕过执行检查。

普通应用只需提供业务输入；无需再维护 Host 轮询、底层 CAS、租约续期或恢复推进循环。

### M2：统一执行授权，保留应用认证边界（P0）

授权分为两个层次：应用认证调用者并决定业务许可；SDK 将该许可转为可校验、可撤销的执行权限。
本地嵌入模式信任宿主进程及其配置的授权提供方，不承诺隔离同进程恶意代码或直接 SQL 写入者。
若以后增加网络入口，必须另行实现传输认证和租户隔离，不能直接公开现有低层对象。

拟议 `AuthorizationContext` 只由可信宿主/适配器建立。持久化主体、租户、策略版本和决策来源供审计；
外部传入同名字段不能自行获得许可。持久化凭据应使用不可伪造的能力引用或受验证的令牌，
不得把 `actor`、caller ID 或哈希比较当成权限校验，也不得在诊断中泄漏凭据。

执行权限绑定 store、Run、task、attempt、generation、部署、操作范围、有效期及独立撤销版本。
SDK 负责签发/引用、验证、向子任务收窄委托和撤销；子任务不能扩大父权限或跨租户执行。
申请新操作、领取任务、开始受管工具/Effect、提交当前结果、应用修订和确认调用方收据时均需检查。
恢复接续要重新验证当前许可；读取历史幂等收据不等于重新获准执行。

暂停、取消和修订改变控制版本，旧的无限制权限失效。默认收尾模式下，SDK 仅为已登记的有限
收尾集合保留或重新签发受限权限；不继续接受旧 worker 的任意请求。结果回收、清理与通知各用
对应范围的权限，使停止业务执行不会同时停止清理。

检查与本地状态变更须在同一权威事务中线性化。外部调用只能由受管入口在授权检查后发起，
取消发生前已被准许的调用仍可能产生副作用，必须登记并核查。绕过 SDK 的任意网络、文件及
子进程行为不在其强制授权保证内；隔离和适配器负责扩大可控边界。

### M3：按 Run 持久化暂停，处理嵌套等待（P0）

暂停请求先记录稳定 request ID、控制版本、模式和收尾范围。调度 outbox 与 Kernel claim
读取同一控制事实或其已确认的版本，不能只在 Host 内存中放一个布尔开关。
登记映射必须早于执行可领取；无法确认映射或控制版本时停止领取该托管执行。

| 模式 | 可以继续的工作 | 完成条件 |
| --- | --- | --- |
| `drain`，默认 | 已启动任务及其已登记的必要子任务依赖链；有界结果回收、通知和清理 | 业务执行已退出或到达持久化 checkpoint，所需资源已释放/隔离，没有阻碍安全修订的未知效果 |
| `interrupt`，显式选择 | 取消投递、结果记录、资源清理及效果核查 | 执行权限已撤销，进程/资源停止证据齐全；未决效果仍保留恢复义务 |

暂停完成不是请求已提交。存在活跃执行、未确认清理或阻碍修订的效果时，报告 `pausing`
及具体 `recovery_obligations`，不能提前报告安全暂停。超时返回当前状态和阻塞者，不自动升级为强杀，
也不把超时记作取消完成。其他 Run 应继续正常领取。

当 B 正在等待 C 时，SDK 登记 parent/child、等待的结果身份、期限和所属执行。
暂停时冻结必要依赖链；C 如果已登记且属于该集合，可在受限权限和原预算内完成，使 B 能收尾。
不允许通过不断新建子任务无限扩张该集合。未登记的依赖、环、缺失子任务或无界等待应被识别并
返回阻塞原因；应用可补充显式方案、提供 checkpoint，或请求中断。
仅存在一个等待描述或正在睡眠的 Python 栈，不代表已到 checkpoint。

还要处理 worker 容量耗尽：所有槽位被等待子任务的父执行占用时，仅允许 C 领取仍不能推进。
托管等待原语必须管理可释放的执行槽位，或在配置的总资源上限内预留子任务推进容量；
不支持让出槽位的同步 handler 必须在接纳嵌套等待前验证容量，容量不足明确拒绝并说明原因。
不能无限增开线程/进程，也不能要求应用另写一个 worker 池来避开死锁。

checkpoint 需包含可恢复输入、已完成步骤、待接收结果及资源状态，由应用声明业务恢复方式，
SDK 负责持久化、释放执行权和恢复关联。dev1 首个闭环必须支持登记依赖链的收尾；
不能以尚未实现的通用 checkpoint 能力作为其通过前提。

并发领取与暂停通过 Kernel 事务确定先后：暂停生效前已获准的执行纳入收尾核查，生效后
不符合例外范围的执行不能领取。跨库环境持久化各参与方的停止屏障并逐一确认，
确认前保持 `pausing`；不能把两个 SQLite 提交声称为一个原子提交。
在任意参与库的屏障写入后崩溃，重启必须沿原暂停请求和控制版本接续，核对已确认与未确认参与方。
已确认屏障继续拒绝范围外领取；尚未确认的参与方按其实际屏障时点登记此前获准执行的收尾义务。
部分写入不能被当作暂停完成，也不能通过 `resume` 跳过剩余参与方的核对。

### M4：可预览、可恢复的同 Run 修订（P0）

引入独立的修订计划记录，复用现有 prepare → commit → activate 的事务结构与幂等经验，
不把 `reopen_run` 放宽为忽略原有终态、效果和清理条件。失败/取消 Run 的既有恢复 API 保持原义。

预览在已观察的 revision、generation、控制版本及部署上计算，输出以下分类：

- 可复用：原结果、内容身份、来源 generation、兼容证据与应用有效性声明。
- 必须重算：变更的 handler/输入/任务、消费者、声明的产物下游，以及等待该结果的父任务。
- 必须先核查：未知外部效果、清理义务、缺失的产物关系或未满足的重试许可。
- 图变化：增删任务和边，旧的已排队命令如何退役，以及新图的环与绑定检查。

影响计算同时考虑任务依赖、嵌套等待和应用声明的产物关系。不能只顺着任务 DAG 找下游，
漏掉等待 C 的父任务 B；没有证明的复用默认不获批准，并在预览中说明缺少哪项声明。

| 阶段 | 持久化内容和前置条件 | 崩溃或重复请求处理 |
| --- | --- | --- |
| Prepare | 冻结计划、预览依据、目标部署、失效/复用集合、预算及授权决策引用 | 相同请求恢复同一计划；不同内容冲突；准备不激活执行 |
| Commit | 重新核查安全暂停、源版本、权限、预算、效果及所有参与库；登记新命令与旧命令退役 | 竞争使计划过期时返回冲突；不能静默扩大影响范围 |
| Activate | 匹配的新 worker 和所有存储屏障就绪，确认新部署可执行；默认仍保持暂停 | 不完整时保持关闭；重试只推进同一事务，不再建另一代 |

建议保留 `revision` 为持久化变更的 CAS 序号；改变执行定义的修订成功提交时只增加一次
`generation`，旧 attempt/命令/收据保留。纯暂停和无修改恢复不增加执行 generation，
使用独立控制/撤销版本隔离权限。这避免把一次暂停伪装成业务重跑，也避免新旧执行共用授权。

新托管修订默认不自动恢复执行。独立的 `resume` 在确认激活完成、无阻塞义务且权限/预算仍有效后，
才持久化开放当前控制版本；无代码修改的恢复也走同样检查。与取消并发时以权威 CAS 决定先后，
已经提交取消的 Run 不能被迟到的 `resume` 重新开放。重新运行已取消 Run 仍需显式恢复授权，
不能通过普通 `resume` 绕过。该规则不改变旧 `reopen_run` 的激活行为。

新 generation 可引用 A 的历史有效结果，但必须有显式复用记录；不能改写 A 的旧命令归属。
失效任务创建新 attempt/命令，旧 queued 执行退役，旧结果可归档和交付历史收据，
但不能满足当前依赖、覆盖当前结果或触发新派发。
通知回调和外部 ACK 的历史欠账不应默认永久阻止安全修订；新协议须将其按原结果身份隔离。
如某个回调仍可修改当前业务产物，则需收尾或按声明作为副作用阻塞。

跨库继续使用可重入的协调记录、参与方准备记录及执行屏障；任何阶段缺失或不可达均不能
激活新 worker。控制入口可在没有业务 handler 的情况下推进协调与诊断，但不能凭空确认部署可执行。

### M5：统一收尾记录，优先恢复未完成步骤（P1，安全前提进入首个闭环）

为每个托管 attempt 建立收尾记录，分别呈现以下事实，不压缩为一个 `done`：

| 事实 | 内容 | 不能据此推断 |
| --- | --- | --- |
| handler 产出 | 候选结果、原始错误、部署及内容身份 | 结果已落盘、子进程已停止 |
| 结果候选已持久化 | 不可变候选及产物引用，记录采集时间和写入状态 | 文件不再变化、业务验收通过 |
| 执行权限撤销及清理 | 进程树/远程资源证据、未决效果、恢复适配器及版本 | 未知外部操作一定没发生 |
| 收尾结果可交付 | 输出封存、清理及效果条件满足后的托管结算记录 | 调用方已收到或接受 |
| 传输与调用方确认 | 原有 notification/result identity、传输报告、经认证的明确 ACK | 模型理解、审查通过或业务完成 |

适配器在可能失败的清理前记录候选结果和原始错误；记录清理义务、稳定资源身份和重试能力。
仍可能被子进程写入的目录只能作为候选。必须确认停止写入并重新封存/校验内容后，才允许应用
按其业务规则接受；路径相同或曾有哈希不能替代该检查。

SDK 先选择只清理、只同步结果、只重试投递或只等 ACK 的恢复步骤。只有业务执行确实需要重试，
且许可、预算、效果及部署检查通过时，才创建新执行。无清理能力或证据不足时保留义务，
不能因失去旧 handler 的导入能力而把资源视为不存在。

旧 Kernel terminal result、已发布失败和 `RequestResultInbox` 的同身份不可变约束继续保留。
后续确认候选可接受时，新增明确关联旧结果的托管结算/采纳记录，并使用新的结算结果身份或
子请求身份交付；不能把同一收据键的失败改成成功。该步骤也须幂等，避免清理恢复重复通知。

先整合现有 sandbox journal、取消报告和请求收据，再定义可供 OpenCode 等适配器使用的恢复钩子。
适配器负责资源和外部效果证据，SDK 负责何时推进及如何记录，不在核心硬编码特定工具错误字符串。

### M6：预算连续、追加可审计（P1，基础累计进入首个闭环）

建立按 Run 归属的预算账本，区分上限、已用、预留和未知用量。暂停、修订、重启、重新激活
默认继承账本与最初绝对截止；历史消耗不能因为新 attempt 或 generation 被归零。

- SDK 计量托管派发/执行及机械重试，分别定义计费点；幂等重复提交不重复扣减。
  原命令 `max_attempts` 仍生效；现有显式效果恢复允许的额外 claim 也需计入 Run 总预算。
- 新执行的期限取 Run 剩余绝对期限与任务 timeout 的较早者。暂停经过的时间不返还，
  `wait(timeout)` 仍只是调用者等待时限。
- token、费用和业务次数由预算适配器提供预留、结算与核查接口。请求前预留，响应后结算；
  响应丢失保留未决预留，不能当作零消耗。未接入计量的外部调用不声称受硬预算保证。
- 预算追加或延长截止需要显式请求、许可和理由，记录前后值；命令重试不能重复追加。
- 业务预算耗尽应禁止新业务执行，但保留受限的取消、清理和结果持久化能力。
  恢复维护额度另行有界记录，不能把它作为继续业务执行的旁路。

### M7：无需业务代码的有界诊断（P1，控制摘要进入首个闭环）

默认摘要拟包含：Run 与控制状态、观测版本、正在执行或等待的对象、待清理/待交付步骤、
实际 handler/部署绑定、旧权限拒绝原因、剩余额度、未知项和下一项所需证据。
业务进展字段由应用提供来源和时间戳，明确标注为应用事实。

复用现有 `get_run_summary`、`get_task`、`list_tasks`、`read_events`、
`inspect_work_availability`、`inspect_cancellation` 和来源查询，不以 `get_run()` 展开完整历史
作为常规状态入口。增加必要的等待关系、预算及收尾索引，保持有界载荷、页大小、时间预算与游标。

每份报告包含 `observed_at`、源版本、`complete`、截断和一致性说明。
跨库状态不是天然原子快照；扫描预算耗尽、来源不可用和确实为零必须区分。
诊断不领取任务、不回收租约、不迁移库、不运行 handler，也不以“建议可继续”授予执行权限。
分页/增量游标绑定观察范围，解释重复和过期行为；审计授权并对敏感输入和凭据脱敏。

## 6. 验收场景与证据要求

### 6.1 首个完整闭环

使用真实 SDK 进程、持久化数据库和独立 worker，固定 SDK wheel、实际导入路径、handler 部署及配置：

1. 同一 Run 中 A 已完成，B 等待已登记的 C；另建对照 Run 持续执行。
2. 请求 `drain` 暂停，验证 C 可在登记依赖链范围内收尾，B 可释放等待；新的无关任务不能领取。
   若 C 无法收尾，验证报告真实阻塞，再显式走 interrupt 和效果核查，不能假定暂停已经完成。
3. 修改 C 的 handler 并生成预览：A 有明确复用证据；C、等待者 B 及相关产物下游进入重算集合。
   A 是结果仍有效的业务声明，不能仅以“曾成功”推导复用。
4. 提交修订，启动与新绑定匹配的 worker；确认激活完成但未自动领取，再显式 `resume`，在原 Run ID 下恢复。记录 C 和相关任务实际执行的
   handler 版本/模块来源；证明 A 的执行计数未增加，旧输入和历史收据仍可读取。
5. 确认调用方通过托管接口取得结果和收尾状态，预算与原截止持续有效，对照 Run 未被暂停。

该场景先证明 SDK 控制闭环，再通过有代表性的真实适配器验证“已产出但清理失败”的路径。
ModPort 的 Minecraft 验收另留应用证据，不能用上述 SDK 场景代替。

### 6.2 必须覆盖的故障与竞争

| 编号 | 注入或操作 | 必须观察到的结果 |
| --- | --- | --- |
| V01 | 两个 worker 与暂停并发，含已进入 Kernel 队列的任务；在每个参与库的部分屏障写入后杀掉控制进程 | 各屏障之后无未获许可的领取，此前执行列入收尾；部分确认重启后仍为 pausing，沿原请求核对所有参与方后才能完成暂停或恢复 |
| V02 | B 等 C、父任务占满 worker、子任务失败、缺失登记、等待成环及暂停超时 | 登记链能在资源上限内收尾；容量不足在接纳前明确拒绝；其他阻塞不能被报告为已暂停 |
| V03 | 预览后状态变化；两次并发修订；重复请求内容冲突；取消与 resume 竞争 | 过期计划拒绝；只有一个修订提交获胜；激活默认仍暂停；已提交取消不能被迟到恢复开放 |
| V04 | prepare/commit/activate 各持久化边界杀掉控制进程，含分库存储 | 重启接续原事务；无窗口同时激活新旧执行权；参与方缺失保持关闭 |
| V05 | 旧 worker 迟到结果、旧租约续期、旧工具请求、跨任务或租户委托 | 拒绝过期/越权操作；保留历史诊断；不能满足新代次依赖或产生新的授权执行 |
| V06 | handler 输出已记录后，进程树或远程 disposal 清理失败 | 输出和原始错误保留；恢复只做清理；业务执行计数和外部效果不增加 |
| V07 | 外部调用响应丢失、效果未知、清理证据缺失 | 保留恢复义务和预算预留；没有证据不得自动重跑或采纳候选 |
| V08 | 结果落盘/传输/ACK 各阶段崩溃或响应丢失，重复恢复 | 历史结果不可变；只重试缺失步骤；重复交付可去重，读取不隐式 ACK |
| V09 | 暂停期间截止到期、预算耗尽、追加请求重放、跨 generation 重试 | 原预算连续，追加只生效一次；业务停止，受限清理仍能继续 |
| V10 | 业务模块导入失败或部署不匹配 | 独立入口仍能解释状态并记录获授权控制；未安装匹配部署不能激活 |
| V11 | 大历史库、诊断预算耗尽、跨库并发写入 | 读量/载荷有界；游标可接续；不复制整库，不把未知当作零或一致 |
| V12 | 旧公开 API 示例、旧库显式升级、旧 SDK 尝试写新库 | 原接口语义不变，历史与未决义务保留，不兼容 writer 拒绝写入 |

验收记录必须关联 Run/task/attempt、generation、命令/结果/效果身份、控制版本、真实部署、
预算前后值、进程和资源停止证据。使用外部计数器或服务记录证明未重复调用；
仅统计 SDK 结果条数不能证明没有重复副作用。

### 6.3 验证层级与完成判据

- 定向事务和边界测试：证明控制规则、冲突处理和状态转换。
- 真实进程、重启及故障注入：证明实际领取、暂停、部署切换和清理，不用单进程 mock 替代。
- 干净环境安装候选 wheel：核对实际导入来源，运行公开接口示例和上述完整闭环。
- 独立审查：重点覆盖授权旁路、暂停/领取竞争、跨库屏障、候选采纳及预算重复扣减。
- 最终回归及平台验证：检查 Linux/Windows、x86-64/ARM64 的声明支持路径和 Python 兼容范围；
  不支持或跳过的条目单列，不借既往 dev0 CI 通过证明 dev1。
- 应用集成验收：handler/依赖/业务策略/适配器证据由应用提供；Host、租约、权限撤销、
  修订推进和收尾重试由 SDK 驱动。示例若仍自行维护这些控制循环，则托管目标未达成。

实施过程必须分别报告“代码完成”“执行已启动”“验收已通过”，并保留尚未验证的路径；
本文不构成 0.7.0.dev1 的发布或能力验证记录。
