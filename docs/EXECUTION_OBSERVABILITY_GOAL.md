## 目标和范围

让应用通过 SDK 公共接口直接回答：某次执行是否实际启动、哪些进程仍可观察、何时有输出或工具活动、
何时有应用声明的进展、正在等待什么、受哪一层期限限制，以及取消和收尾完成到哪一步。
应用启用停滞策略后，SDK 持久化观察窗口并可靠通知应用；应用决定继续观察或执行获授权的处置。

本轮包含五项能力，通用流与子进程观察器属于第一项：

1. 活动上报、真实启动阶段、逐 execution 查询及有界流观察。
2. 权威有效期限与剩余预算，贯通 SDK、子任务和工具适配器。
3. 结构化等待链、资源占用和有界嵌套执行容量。
4. 结构化退出、取消请求、进程停止、清理、结果与交付的分别呈现及恢复。
5. 可选的持久化停滞窗口、事件订阅和不被业务容量阻塞的通知处理。

大输入和产物引用的通用整合列入后续，不阻塞本 Goal。SDK 自身的调度与结果交付仍须证明输入真实到达消费者。
不在本轮增加完整的 Run 修订系统、可信多租户授权服务、模型计费系统、跨机器自动接管或新数据库后端。
SDK 核心保持标准库与 SQLite；提供方协议、业务进展解释和验收规则由适配器或应用提供。

本轮只修改和验收 `/root/dispatcher-sdk`。ModPort 的接入、生产调用链、模型提供方协议、
外部服务和 Minecraft 迁移不属于完成条件；不修改其他仓库，也不为通过其现有适配器而添加 SDK 特例。
应用侧可以按 SDK 公共契约调整代码，既有跨项目证据保留为历史材料。

质量要求贯穿上述五项能力：

- 功能完整性：公共入口、持久化、查询、执行、返回及恢复形成闭环，提供清晰的类型、错误语义和可执行示例。
- 鲁棒性：真实并发、SQLite 争用、部分提交、进程崩溃、取消竞争及时间边界下保留原始事实；
  暂态重试使用同一原始预算，恢复不重复业务，不以延长期限或隐藏未知状态换取通过。
- 可维护性：控制权、状态转换和恢复义务有明确归属，复用现有预算、取消及通知机制；
  收敛本轮新增的重复逻辑，避免为单一应用增加分支或并行账本，不做无关的全仓重构。

外部应用报错只作为排查线索。先检查调用是否遵守 SDK 契约，再在 SDK 仓库内建立最小复现，
区分 SDK 缺陷、测试时序问题和应用适配错误；已证实的 SDK 缺陷仍必须修复。
无法复现的集成问题不得直接归因于任意一方，也不得据此扩大本 Goal 的跨项目范围。

## 可验收的实施 Goal

> 在保留现有公开 API 和显式存储升级语义的前提下，完善上述五项 SDK 能力的功能完整性、鲁棒性与可维护性，
> 通过本文 A01 至 A18 的必需场景：安装后的公共接口在 Linux 真实进程中独立完成闭环，
> Windows 完成进程观测、期限终止与清理验证，现有 OS、CPU 与 Python 支持矩阵对同一候选通过 CI。
> 每个场景都有可复现命令、实际导入来源、执行身份、原始观察和判定依据；独立审查发现的问题已解决。
> 未验证、失败或跳过的必需项均不得计为完成；SDK 提供权威期限、活动窗口与投递机制，
> 不要求应用自行拼装这些内部机制。ModPort 和其他应用的适配不属于本 Goal。

实施完成必须同时满足：

- G1：T01 至 T09 交付物完成；A01 至 A18 每项在指定适用环境得到 `passed`，无未解决的阻断问题。
- G2：新增接口从安装后的 SDK 可调用，具备公共导出、类型、文档和可执行示例；应用可通过高层入口使用，
  不需要拼装租约、fence、SQL、活动刷盘或通知确认循环。
- G3：Linux、Windows 与 CI 证据指向同一候选代码；后续相关变更使受影响证据重新待验收。
- G4：原 API、状态与收据含义保持兼容；需要升级的存储有显式路径，历史执行事实及未决义务保留。
- G5：完成针对本轮变更的可维护性审查，明确状态与恢复归属，处理重复机制和应用专用分支；
  能力限制准确记录，包括未注册子进程、跨命名空间不可见、线程不能强制终止，以及外部监管的责任。

本次规划交付的完成条件是：本文范围与用户确认一致、任务依赖明确、场景具备触发/预期/证据/失败判据、
平台责任明确、独立审查问题修正、链接和文档差异检查通过。它不满足上面的实施完成条件。

## 行为契约

### 活动和状态

SDK 自动报告其拥有的排队、worker 启动、handler 实际进入、终止与清理事实；
模型请求、工具活动和应用进展由对应适配器报告。发送 invoke 或创建子进程不能代替 handler 已进入的确认。

每条观察关联现有 store、Run/task、execution、attempt 及有效执行代际；自动从可信运行上下文绑定，
普通应用不必传 fence。来源、观察时间、最近采集时间、完整性及未知原因必须可查询。
旧 attempt 的迟到报告可保留历史诊断，但不得刷新当前执行的状态、计时或监管窗口。

driver、worker、已注册 agent 子进程分别显示 `alive / exited / unknown`，并保留观察时间和依据。
不支持进程状态的平台或命名空间返回 unknown；过期的 alive 只是历史观察，不能伪装为当前存活。
子进程需要 SDK 或适配器登记；不承诺发现任意未登记、远程或脱离监督的进程。

stdout/stderr 字节、模型事件、工具活动、应用进展分别计数和计时。
首字节、最近字节、首模型事件、首文本可由适配器分别报告；收到原始 chunk 即更新字节活动。
SDK 只记录应用声明的进展及来源，不推断报告内容真实、产物有效或业务通过。
心跳、日志和重复报告不得清零无实质进展时长。
从未输出时同时返回首输出缺失和从相应启动基线计算的等待时长；未接入的指标返回 unknown，不能当作零。

活动先在采集侧更新，按有界批次持久化，不按每个字节写 SQLite。
查询区分即时观察和已持久化观察；崩溃可能丢失尚未刷盘的尾部，必须暴露采集缺口，不能承诺零丢失。
普通遥测故障不制造业务审批门槛；标记降级并保留真实执行结果。等待登记、预算与取消仍使用原有权威控制规则。
遥测队列、写入及锁等待均有界，不得长时间占用执行控制锁；本地硬截止 supervisor 独立于遥测刷盘。
整个存储不可用时，取消提交有界返回 pending/unknown 或明确错误，不假报已提交；
已经接受的停止请求和本地硬截止仍能停止 SDK 拥有的进程，待存储恢复补记尚未持久化的收尾义务。

### 预算和期限

SDK 提供 Run 绝对截止、当前 execution 的实际执行期限、父调用约束、工具局部期限及各自来源。
有效工作期限取适用约束的最早值，并显示限制层和剩余时间；未接入外部期限时不能声称全面覆盖。
收尾预留只扣一次，分别说明工作截止与外层硬截止。具体阶段预留比例由应用配置。
`Task.wait(timeout)` 仍只是调用者等待时限，不隐式改变任务执行期限。

进程内耗时使用单调时钟；持久化绝对期限采用已有 SDK 时间约定。
跨重启不得直接复用旧进程的 monotonic 值。重启、重试和租约续期不得延长原截止或归零已消耗额度。
检测到壁钟回拨或恢复时无法建立可信的经过时间时，不能只用 `max(wall_time, watermark)` 继续计时，
也不能从旧剩余时间重新发放额度。同一宿主可依据仍有效的单调时间域重建保守剩余时间；
无法证明时间连续性时，将预算视图标为未知并停止接纳新的业务执行，保留有界清理能力。
这属于执行期限无法建立的控制错误，不能自动解释成业务失败或要求额外业务审批。
预算耗尽后停止新业务工作，受限清理与结果保存采用单独有界维护额度，不借维护继续业务执行。
托管执行的 Run 截止必须约束已经运行的工作，不能仅在下一次 claim 时才生效。

### 等待和容量

等待记录至少包含等待者、被等待对象/资源、原因、开始时间、适用期限和已知占用。
内存、worker 槽位、子任务结果、工具响应和外部服务分别表达；未接入资源的用量不得虚构。
父子等待的登记必须和实际调度、返回失败关联，涵盖子任务失败、取消、缺失、循环依赖及父退出。
跨库关联采用有界、可恢复的登记协议；部分成功必须可见，不宣称跨 SQLite 原子事务。

首轮保证配置资源上限内的一层真实父子等待可以推进；嵌套链和环的诊断不能截断成无等待。
可挂起的执行让出可释放槽位；同步 handler 可由 SDK 预留受限子执行容量。
无法满足容量、深度或资源要求时，在接纳等待前明确拒绝并撤回本次未使用的预留，不能无限增开 worker。
活着的父进程继续计入内存占用；让出槽位不释放其内存。

### 退出和收尾

分别记录启动失败、资源准入超时、执行超时、Run 截止耗尽、主动取消、信号退出及有证据的 OOM。
错误分类保留原始返回码、异常和证据来源。退出 137 或共享 cgroup 的 OOM 计数不能单独归因为该进程 OOM。
Linux cgroup、Windows Job 和远程后端细节留在平台适配层。

取消已请求、执行权撤销、进程已停止、资源清理确认、结果落库、传输投递和调用方 ACK 分别呈现。
结果或原始错误先保留，清理失败留下恢复义务；重启恢复只推进缺失的清理/投递步骤，不重跑业务。
未知外部效果继续走既有恢复语义；线程模式不能把撤销执行权当作线程已终止。

### 停滞和订阅

默认不启用自动停滞处置。应用配置所观察的指标、采样周期、连续窗口数、等待豁免及通知目标；
“十分钟观察一次、连续三次”仅是应用可选配置，不硬编码为 SDK 规则。
总截止不因等待豁免、输出活跃、监管继续观察或重启而延长。

只有具备有效观察基线的完整窗口才计为一次无进展窗口；观察失败和关机空档标为未知，
不补造三个失败窗口，也不清除已确认的历史窗口。无法证明观察连续性时，中断当前连续计数并重新建立基线，
历史窗口仍可查询；这不表示已有实质进展，也不能把无进展时长改报为零。
等待豁免暂停计数，并显式显示原因与等待时长；豁免期间若观察中断，同样重新建立连续窗口基线。
新进展结束当前停滞 episode；后续新的停滞形成新 episode，重复进展报告不重置窗口。

窗口推进和告警入队使用同一持久化提交，或等价的可恢复提交协议。
一个策略版本、execution attempt 和 episode 对应一个稳定通知身份；跨进程竞争只生成一项逻辑告警。
投递按至少一次处理，重试沿用原通知身份。SDK 自带持久化收件去重；应用外部动作仍需幂等。
公开区分 pending、delivering、已持久化接收、已消费和 dead/重试耗尽；投递 ACK 不等于应用已消费。
重试耗尽保持可查询，通过高层支持的重投入口沿用原通知身份恢复，不新造 episode 或重复本地消费。
停滞处置必须在控制动作提交点条件检查 attempt、episode 和已确认的进展 revision，
与进展确认使用同一串行化边界或等价条件提交；只在回调开始时读取一次不够。
已被 SDK 接收确认的新进展若先于停滞取消提交，后者必须因过期而拒绝；异步缓存的报告不得伪称已确认。
该条件只约束基于停滞通知的处置，普通显式取消保持既有含义。

窗口评估和通知入队不占业务 worker；同步回调有独立、有界执行容量与故障隔离。
若监管者本身是 agent，应使用显式、有界预留容量，并受内存及预算约束；资源不足须可见，不能宣称监管一定能启动。
回调异常、迟缓或永久阻塞不得阻止 SDK 截止、取消与其他告警入队，也不能无限创建线程。
SDK 进程退出后，需要外部宿主 supervisor 启动同一存储的受支持恢复流程；本轮不实现外部服务管理器。

## 公共接口交付要求

T01 固定最终命名和签名，以下为能力契约，不是已存在的 API：

| 调用方 | 必须能够完成的动作 |
| --- | --- |
| handler 或适配器 | 从 HandlerContext 获得自动绑定身份的活动上报、预算和受管等待能力 |
| 普通应用 | 从 Task/Dispatcher 或等价公开句柄读取逐执行快照和收尾状态，启用/恢复停滞订阅 |

涉及 schema 的修改提供显式升级，不在普通读取时初始化或迁移数据库；不兼容 writer 必须拒绝写新布局。
有界查询使用分页/增量游标，读操作不续租、不推进通知、不清理进程、不写持久化时钟。

## 测量参数与证据格式

T01 固定可重复的测试配置并随证据保存。真实时间场景建议使用 1 秒采集刷新周期、3 个 2 秒停滞窗口、
不少于 10 秒的外层硬期限；测试预先声明调度误差容忍值，不能失败后不断放宽。
无换行输出必须在下一次字节写入或换行发生前被观察到；硬截止测试同时检查停止证据，不能只看数据库终态。
注入故障测试以实际到达持久化/执行阶段为触发，避免仅靠短 sleep 猜时序。

初始资源预算为：诊断每页最多 50 条明细、每次最多 256 KiB 编码输出、3 秒读取预算；
stdout/stderr 默认各保留最多 64 KiB 尾部。T01 为活动队列和批量写入另设明确有限上限并测试溢出语义。
这些是本轮目标配置，不代表当前 SDK 已具备这些默认值；若实现前需调整，应在契约中记录理由与替代验收值。
需测量启用前后吞吐、延迟和持久化写入量，报告环境及退化；不能靠关闭关键观察获得通过结果。

每个场景记录：场景编号与适用环境、命令、开始/结束时间、候选来源、实际 import 路径、配置、
host 提供的 Run/task/execution/attempt 身份、预期/实际、原始证据位置、结论及未知项。
结论只用 `not_run / running / passed / failed / blocked / not_applicable`；
`blocked` 写明缺少的平台/权限/服务/证据，`not_applicable` 需说明能力在该环境确实不适用，不能隐藏必需项。

沿用 host 提供的来源字段；不新增或运行 SHA、checksum、fingerprint 验证，
不新增 source_fingerprint、candidate 或 rubric 身份比较门槛。历史 Run 证据不改写。
需要确认文件或数据未被改写时，使用受影响记录、只读连接约束、写操作跟踪及既有宿主证据，不另加摘要检查。

## 平台和 SDK 独立验收要求

本次读取的 [CI](../.github/workflows/ci.yml) 为以下矩阵；执行时需重新核对，不能悄悄缩减支持范围。

| 环境 | Python | 本 Goal 要求 |
| --- | --- | --- |
| Linux x64 | 3.10 至 3.13 | CI 全通过；至少一个候选安装环境完成 A01 至 A16 全闭环 |
| Linux ARM64 | 3.10 至 3.13 | 原生 CI 全通过，执行适用进程、预算、等待和恢复场景 |
| Windows x64 | 3.10 至 3.13 | CI 全通过；至少一个原生候选安装环境完成 A17 |
| Windows ARM64 | 3.11 至 3.13 | 原生 CI 全通过；至少一个原生候选安装环境完成 A17 |
| Windows ARM64 主机与 x64 Python | 3.10 | 保留当前模拟兼容 job；不能代替 ARM64 原生证据 |

CI 可承载原生平台的真实进程验收，但必须执行新增场景，不能只有 import 或 mock。
Linux cgroup 专属检查在 Windows 可以不适用，Windows 的进程停止与清理证据则不能跳过。

A16 使用 SDK 仓库自有的独立消费程序，从源码目录外导入已安装 wheel。
本地子进程或受控流/工具服务提供确定性的字节、等待、成功和错误；它们替代应用业务载荷，
不替代 SDK 的实际调度、持久化、进程控制、预算传播、取消及恢复路径。
不需要模型凭据、外部服务或 ModPort 代码；不声称这些夹具验证了任何外部提供方协议。
单模块用例用于定位问题，A16 另需通过公共入口贯穿实际执行及结果消费，避免只凭接口存在判定完成。

进程跨命名空间检查由能观察其启动环境的宿主执行；外部 driver 生存与恢复验证采用独立宿主 supervisor。
必须跨越操作回合的 Run 使用持久服务托管，验证启动命令返回后仍存活；重启接续同一冻结 Run 和原预算。
短验收进程可以在有界测试 harness 内完成，不把会话 exec 当作长期部署。
