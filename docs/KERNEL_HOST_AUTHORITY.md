# Host authority for protected Kernel Runs

Protected Runs require an `authority_verifier` installed by the host in every process that performs Kernel operations. The verifier is a trusted, bounded, nonblocking function: it authenticates the supplied credential against the host's actual authorization and control state and returns claims. Merely copying a caller's claims does not establish authority. Verification is performed inside the Kernel write transaction, so a blocking verifier delays other writes and revocations. The host must enforce its control leases and serialize cancellation and revocation writers across both participant stores.

The worker's verified claims include a nonempty `principal`, `expires_at`, scoped `permissions`, and the exact `run_id`, `generation`, and `control_epoch`. Each protected submission, claim, start, effect, child, or supervisor admission verifies the relevant permission and the current durable local authority. Settlement of work already admitted can still record outcomes after a fence.

For a selective split-store pause, the host may authorize an already registered execution in the durable drain set. The pause credential's verifier returns `drain_pause` with the exact operation, Run, generation, new control epoch, both store identities and canonical drain IDs; Kernel binds that proof into the local barrier. The original worker credential retains its source epoch and principal, grants the action and `kernel:drain`, and its verified claims include `drain_admission`: `allowed: true`, the pause `operation_id`, `run_id`, exact `execution_id`, `generation`, the new pausing `control_epoch`, `kernel_store_id`, `orchestrator_store_id`, `orchestrator_incarnation`, and a live `expires_at`. The host must independently authenticate the matching Orchestrator pause decision and participant identities, and serialize its proof against cancellation and revocation. Kernel checks its own identity, barrier, epoch, membership and each requested action transactionally. New child work and external effects are blocked; already authorized outcome settlement remains available. Completing the local pause or cancelling the Run closes this admission.

For a protected initial generation that has not passed through a revision resume, the host first calls `bind_initial_admission` while the Kernel Run is paused. Its verifier authenticates the exact committed Orchestrator receipt and both participant store identities; Kernel stores that immutable binding. Worker verification must return `global_admission` with `open: true`, the matching `run_id`, `generation`, and `control_epoch`, and the exact bound `orchestrator_receipt`. The host must authenticate the current open state and receipt from the actual global admission state, not from the worker's input. Missing, mismatched, or closed admission denies business work. The coordinator must fence cancellation in Kernel before reporting it committed; hosts must serialize gate decisions and cancellation so stale admission proof cannot be issued during the transition.

For a resumed generation, the verifier must return a live `control_lease` containing `held: true`, `lease_id`, `lease_fence`, and `expires_at`. Its lease ID and fence must match the durable Kernel resume decision. It must also return `global_admission` with `open: true`, the resume `operation_id`, `kernel_store_id`, `orchestrator_store_id`, `orchestrator_incarnation`, and an `orchestrator_receipt`. The receipt is the exact host-authenticated committed Orchestrator open receipt: `operation_id`, `run_id`, `generation`, `control_epoch`, `state: "active"`, `committed_at`, `kernel_store_id`, `orchestrator_store_id`, and `orchestrator_incarnation`. Kernel compares its bindings to the durable resume decision on every business operation. The host must confirm that the receipt is committed and still authoritative and that the same exclusive lease is live; the values are not proof merely because a caller supplied them.

Revision activation and resume are separate. Activation records a paused participant receipt. Kernel resume advances the local control and worker binding, but business admission stays closed until the verifier can authenticate the final Orchestrator open receipt and the live lease. Losing either proof fences subsequent business entry. Already admitted work and external effects require their own cleanup evidence; a pause, activation, or resume receipt does not establish cleanup. Hosts must keep the lease valid through the cross-store opening and subsequent worker checks, or implement a separately authenticated transfer of authority.

The development API supports a host-authenticated control lease takeover. The host must prove the exact original operation and participant stores, current exclusive successor lease, and exclusion of the previous holder. A durable takeover receipt records the transfer; historical receipt inspection does not itself grant current admission. A successor may inspect a pending takeover under its own verified authority to distinguish a committed receipt from transactionally confirmed absence; inability to authenticate that inspection is unknown. Worker entry still requires the current lease and committed global open receipt. The SDK cannot itself establish exclusion of writers in an external host.

External application projection participants are bound to the revision and source application version. The host authenticates the participant requirements, exact execution scope declarations and durable participant receipts. The application adapter must atomically compare its source version and enforce the current lease fence on writes; it must durably record the result before acknowledging it. The Kernel gates only execution scopes that declare a dependency on that participant. The adapter receives a complete Run projection, so the host must trust it with that data. Neither these receipts nor Kernel checks make an external store transactional or prove that an adapter implemented its host obligations.

Each installed revision must have a durable application budget policy before resume. `install_budget_policy` requires the verifier's exact `budget_policy` and `kernel:manage_budget` permission. The policy binds `policy_id`, `decision_id`, Run, generation, both store identities, and up to 32 scopes of `{owner, unit, source_id}`. An explicit empty `scopes` list declares that the generation has no application budget dependencies. Otherwise, the host calls `declare_budget_dependencies` with its authenticated exact Run, generation, policy and decision IDs, both participant identities, execution ID, command and scope subset; its verifier returns that `budget_declaration` and `kernel:declare_budget` permission. Declarations are immutable and may explicitly contain an empty scope list for unrelated work. A nonempty declaration also requires worker verification to return `budget_admission` with `allowed: true`, the exact Run, generation, policy ID, decision ID, both participant identities, execution ID, scopes and live `expires_at`, plus `kernel:budget` permission. The host must independently evaluate current ledger availability and serialize changes and revocations through the Kernel transaction's commit. Kernel does not impose external provider hard limits. Outcome settlement remains available after budget admission closes.

For a transaction that checks more than one execution, such as a dependent parent submitting a dependent child, the verifier may instead return `budget_admissions`: up to 16 distinct execution-bound admissions, with the same fields and checks as the single form. Supplying both forms, duplicate execution IDs, or omitting a required execution is rejected. `ChildService` can ask the host's `child_budget_declaration_provider` for the exact generated child command's credential and declaration before submission. The provider is trusted to be bounded and nonblocking; the SDK checks the original deadline after it returns but cannot interrupt a stuck synchronous provider. This hook does not itself evaluate budgets or establish a live application adapter.

Child submission and adoption carry one admission budget through registry validation, lifecycle locks, lookup and Kernel admission. This is not a hard wall-clock completion bound: synchronous validation or lookup cannot be interrupted by this deadline, and an already admitted transaction can finish after it expires. Hosts must bound their own synchronous callbacks. If a caller stops waiting, it must reconcile the exact child ID and parent generation because the operation's result may be unknown.

Untargeted claims inspect at most 64 budget-blocked candidates per transaction. `BudgetScanContinuation` means the scan is incomplete: retry the same revision predicate with `budget_scan_cursor=error.cursor`. Each retry applies its current exclusions. A cursor does not settle or authorize skipped work. At the end of a scan, the caller starts a fresh scan on its next poll so earlier candidates can become eligible. Claims and continuations impose bounded predicate and execution-ID sizes.

Legacy import also requires a host-authenticated, continuously enforced writer-isolation lease and complete source membership and budget evidence. Imported pages remain paused and incomplete until a terminal receipt. No API in this document establishes that an existing application or deployment has provided these host guarantees.

For a supervisor outcome left unresolved after its parent exits, `reconcile_supervisor_result` accepts an exact original lease, result, budget envelope, existing Kernel store ID and cleanup evidence. The verifier must independently authenticate the complete `supervisor_result_reconciliation` decision and grant `(execution_id, "kernel:reconcile_supervisor_result")`; the decision contains `kernel_store_id`, `lease`, `result`, `budget_envelope`, `cleanup: "confirmed"` and `cleanup_evidence`. Authority and store identity are checked in the Kernel transaction and again before commit. The host must serialize revocation and cancellation and establish actual cleanup and the original outcome and timing independently. A raw supervisor packet is an observation, not authority to settle. Exact replay is supported while the generation remains current; unresolved effects, stale generations, unknown clocks and invalid authority remain closed. A copied database retains its logical store ID: matching it does not prove a unique physical writer or host isolation.
