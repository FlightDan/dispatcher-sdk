## 2026-11-01 增量与仍需验收的边界

2026-11-02 补充：进程启动前若能确定尚未尝试创建进程，SDK 将原结果和精确代次的 `sdk_supervisor_not_invoked` 责任结论在同一 Kernel 事务内提交；注册回执不确定、预算采样待对账和完成时钟待恢复的路径保留该证据并在恢复时核对。实际创建调用结果不明时仍保持责任未知，不能依据缺少启动回调解除。诊断事实写入前不可保留时，已领取代次的持久生产者保持开放，并在停止报告中给出本地未知计数；宿主恢复须独立证明生产者死亡且承认缺失证据。新修复的定向回归已通过；完整源码测试、最新安装包和平台 CI 尚待完成，真实旧 Run 接入按宿主后续计划单独验收。

当前 `0.7.3` 候选 wheel 已在全新隔离目录导入并通过 78 项定向测试：清理责任 12 项、生命周期和嵌套真实进程 38 项、双库接入/预算/观测 26 项、受管业务全路径 2 项。新增全路径用例在合成旧库上串联暂停、修订激活、恢复、预算拒绝与撤销、两次独立进程 handler、结果消费后再提交及重开核对；宿主凭据和旧库初态均为夹具，不能据此声称真实 ModPort 旧 Run 或预算提供方已验收。全量源码与跨平台 CI 结果另计。

- 开发树的 Kernel 目标已升至 schema 12，Settlement Journal 新建目标为 schema 4；旧 Kernel v11 与 Journal v3 需要分别显式复制升级。v12 为生命周期事件设置按执行代次的退役水位；v4 使用独立的 `(Kernel store ID, outbox sequence)` 回执命名空间。接收前核对 Kernel 实际 outbox 行的执行身份、阶段和内容，避免任意旧 note ID 或伪造执行身份充当回执。
- 已提交、已确认且生产者真正静默的代次可以由宿主显式分批退役；对应 v4 回执和 note 可在核对退役水位后显式分批裁剪。裁剪会删除诊断历史，宿主须先确认所需消费者、审计保留和旧 writer 隔离；SDK 不自动裁剪。旧普通 note、其他 Kernel 事件与不在裁剪范围的账本仍会增长，不能宣称全部元数据有界。
- v11 待投递事件若在升级前已有同 ID 普通 note 而 ACK 丢失，单靠旧记录无法区分真实交付与碰撞；v4 对此拒绝推断并保留待处理。现提供显式 `reconcile_legacy_lifecycle_receipt`，要求宿主独立证明该原 note 确为目标事件的接收提交；SDK 在写入映射前再次核对两库精确记录和宿主证明，之后由正常投递路径 ACK。拒绝认证时保持 pending，不能凭内容相同自动放行。事件内容在首次持久写入前丢失时仍不可还原；生产者责任只能标记精确代次的未知，不能补造事实。
- 跨库取消在 Orchestrator 本地写入持久意图后，恢复路径会在调用 Kernel 前和提交本地开放时重检同 Run/代次意图。定向竞态测试覆盖 Kernel fence 延迟期间的本地拒绝；宿主仍须在取消两库回执闭合前维持 Kernel 准入屏障。
- 本地定向测试中，生命周期交接 21 项、Kernel 存储升级 15 项，以及退役、结算回执和跨库取消等相关用例通过。它们不证明真实旧 Run、旧二进制隔离、完整平台矩阵或当前安装包验收。已知实现缺陷闭合前不触发 CI；旧 Run 真实接入按宿主计划后续验收。
- 当前源码已构建并隔离安装为 `0.7.3.dev1` wheel；从隔离目录导入的模块提供新退役及回执 API。仅完成静态导入和接口存在性检查，尚未运行该安装包的完整真实进程用例。首次构建因 pip 默认缓存目录只读失败，改用临时缓存后构建成功；该失败未产生发布制品。

## 核验边界

- 当前 schema 11 源码的合成旧布局受管流程重新通过：`apply_managed_operations` 提交任务与应用进展，独立进程执行 handler 并结算；模拟宿主在独立 SQLite 中登记生产者，确认前核对实际 journal。测试使用替代的既有摘要及注册表版本函数，不证明真实宿主所有者隔离或现场旧 Run 接入。另一跨进程暂停、激活和恢复测试也使用该模拟验证器通过，覆盖独立 handler 进程和结算；各参与进程使用非哈希测试令牌替身。
- schema 11 的生命周期责任和实际已写入事件可跨进程保留；最新生命周期整组 21 项及授权、跨进程测试 14 项通过，迁移与既有恢复测试 23 项通过。测试替换注册表版本计算，没有运行摘要或指纹验证。本地测试覆盖生产者崩溃、接收端提交后确认丢失、同执行顺序、不同执行轮转、受管接收回执核对及取消前预留。预留或写入失败后崩溃时缺失内容仍未知，不能补造。可信宿主须记录 token 与真实所有者的关联，并独立验证接收提交和生产者死亡；测试使用模拟宿主，尚未证明真实宿主接入。已投递内容可按显式截止位置裁剪，但事件 ID 和生产者元数据目前仍无界增长。详见[开发接口说明](SDK_DEVELOPMENT_INTEGRATION.md)。

- `recover_claim_lifecycle` 现在可将已提交的 `sdk_confirmed_supervisor_cleanup` 责任结论按原 execution、attempt 和 fence 恢复到诊断 journal。8 项定向测试覆盖 Kernel 关闭重开、写入后确认丢失、投影进程写入后退出及幂等重放，以及不同来源、损坏和超大结论保持未知；不将该结论改写为原始进程树清理回执。独立审查未发现该投影的正确性阻塞。生命周期事件在 Kernel 或 journal 持久保存前丢失时仍不可重建；后续持久队列的实现和验证见上一条记录。
- 已修正打包、隔离消费者和运行时身份测试中针对当前源码的过时 `0.7.2` 版本断言，并同步贡献指南；当时仅运行 3 项打包静态测试。隔离消费者和运行时身份测试在该阶段尚未运行；未推送或触发 CI。
- 现场隔离安装的较早 `0.7.3.dev1` 候选包复现了旧 Run 接入受管模式后，ModPort 后续任务和进展提交遭 `managed Run operations require the controlled managed interface` 拒绝。原有合成生命周期测试直接向 Runtime 提交执行，未覆盖 ModPort 的组合事务。开发树现提供受控 `apply_managed_operations`：原子提交任务、应用状态和游标，校验宿主授权、租约、恢复来源及双库代次；普通接口仍拒绝受管 Run。新候选 wheel 隔离安装到 `/tmp/sdk-managed-install` 后，4 项权限、回滚与重放定向测试通过；另有 1 项合成旧布局接入测试通过，覆盖新事务、outbox、独立进程 handler、结算同步及重开读取。测试使用模拟宿主证明，并替换现有摘要与注册表版本计算，不证明真实宿主隔离。ModPort 必须改用受控接口并为新执行生成受管身份；生产依赖和原 Run 未改动，真实旧 Run 的后续派发和业务验收仍未完成。
