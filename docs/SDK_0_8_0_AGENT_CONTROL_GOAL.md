# Dispatcher SDK 0.8.0 Agent 控制层：实施 Goal 与验收合同

日期：2026-11-03。状态：实施中；进度见 [验收记录](SDK_0_8_0_AGENT_CONTROL_ACCEPTANCE.md)。本文件不是实现、测试或发布完成证明。

## 1. 可验证目标

在 `/root/dispatcher-sdk` 的本地 `release/0.8.0` 分支实现并验证声明式 Agent 控制层：用户通过 YAML 或等价 Python API 定义 Agent，SDK 通过 OpenCode 实际启动、协调、续接和停止执行。用户无需自行拼装执行代次、租约、消息去重、结果消费和恢复协议。

只有第 7 节所有必需验收项具有对应当前制品的有效证据、独立审查无未解决阻塞项、文档与实际默认值一致时，才能报告目标完成。启动成功、模型有输出、合成测试通过或测试总数增加均不单独满足目标。

本文件自包含，后续执行者无需读取原聊天才能理解目标。执行本 Goal 表示采用下列计划默认值；它们不是已经实现的事实。

## 2. 范围与执行边界

- 实施开始时核实工作区、当前分支、既有改动和 `main` 基线。创建本地 `release/0.8.0`；若同名分支已存在，核查后接续，不删除或重置。保留本文件及用户改动。初始开发版本为 `0.8.0.dev1`。

- 不直接复制 ModPort 的 AGPL 实现进入本 Apache SDK；基于公共协议独立实现通用能力。
- 保持现有 Dispatcher、Orchestrator、Kernel 公共接口及核心标准库依赖边界；YAML 作为可选依赖。
- 首版运行时为 OpenCode；不实现 TOON、其他模型运行时、动态生成新角色、自动知识提炼或向量数据库。
- 发布权限不包含在本 Goal 中：不推送远程分支、不建 tag、不发 Release、不发布远程 Wiki。允许更新仓库 Wiki 源文件、CI 配置和生成本地导出预览。远程操作遵守用户已有明确授权；权限不足不代替验收。

## 3. 必须交付的公共能力

### 3.1 API、配置与宿主

- 在 `dispatcher_sdk.agents` 提供 ApplicationSpec、AgentSpec、AgentApp、AgentHandle、Invocation、AgentRun、AgentRef、ArtifactRef 和 RuntimeAdapter。
- YAML 与 Python 配置转换成同一类型化定义，使用同一套校验、默认值、权限和调度。
- `app.coder(...)` 与 `app.agent("coder")(...)` 等价，支持 input、request_id，以及服务调用的 session_key。
- 未传 request_id 时生成并返回；稳定请求 ID 重放返回同一逻辑调用，内容不同必须报冲突。
- Invocation.wait 仅等待本调用；AgentRun.wait 等待所属有限任务链，不等待空闲服务永久退出。
- 提供配置校验、有效配置查询、serve、status、stop、resume CLI。serve 为可受系统服务管理器托管的前台宿主，不自动改系统配置。
- 关闭 AgentApp 时不得伪称后台宿主仍存在。持久服务需独立 serve 进程；完成证据包含客户端退出后服务仍能接收调用。
- OpenCode 由 SDK 启动，使用宿主控制的独立配置与工具注册；明确兼容版本，禁止静默继承与声明冲突的全局或项目工具权限。模型凭据来自宿主配置，日志脱敏。

### 3.2 默认值合同

`schema_version: 1`。普通配置按 SDK 默认、应用默认、Agent 配置、允许的调用覆盖解析。映射按字段合并，列表整体替换；省略表示继承，空列表表示清空，null 仅对明确允许的字段有效。权限与预算始终受宿主上限约束。

| 配置 | 默认行为 | 必须支持的覆盖或限制 |
| --- | --- | --- |
| name / tags | YAML Agent 映射键为唯一名字；标签为空 | 显式标签；标签不充当权限 |
| soul / prompt | soul 可省略；prompt 或调用输入至少提供任务说明 | 文件引用；调用冻结实际内容和配置版本 |
| runtime / model | OpenCode；模型从应用配置继承，缺失时报错 | 模型、推理设置、明确列出的回退；不硬编码 ModPort 模型 |
| lifetime | task | task、service |
| instance | 按任务创建预声明角色实例 | 固定实例、按输入键分组；不允许模型新增角色或扩权 |
| trigger | inputs_ready | 显式调用、消息、定时、状态事件；无上游输入的入口等待调用，不自行循环启动 |
| session | 任务按问题范围续接；服务按会话键续接 | 每次新建、按键续接；服务缺键时报错，不混入全局会话 |
| mailbox | 同会话 FIFO；最多 100 条待处理消息 | 排队、拒绝、替换未开始请求、取消并确认清理后替换 |
| concurrency | 全应用 4 个活动 Agent；每会话 1 个 | 应用与角色上限；同一原生续接会话始终单写者 |
| resources.memory | 应用内存预留容量未设置，默认关闭该准入限制 | 可设置总容量和角色预留字节；开启后每个可调度角色必须声明正数预留；只承诺调度预留核算，不冒充 OS 内存硬限制 |
| access | 宿主可提交；显式依赖边授权相应数据触发；其他 Agent 调用默认拒绝 | invoke、send、read_artifacts、cancel、resume 分别授权；身份由宿主绑定 |
| files | SDK 文件工具级限制；项目读写列表为空 | 读写路径、只读共享输入、strict 模式；写允许相应读取 |
| tools / network | 必要 SDK 控制工具及明确声明能力 | shell、额外 MCP、网络工具默认关闭；模型网络使用宿主运行时配置 |
| workspace | 每任务实例或服务会话私有可写目录 | 只读输入、独占持久目录、显式共享目录 |
| completion | response：响应结束且声明的必需输出已提交 | goal：注册验证器返回通过、继续修复或阻塞；验证器异常单独分类 |
| output | 默认响应，无额外必需产物 | 命名文本、结构化值、文件及必需性 |
| budget | 每个外部请求链 3600 秒、64 次 Agent 调用、128 次模型轮次；不设 token 上限 | 排队即开始计时；重试、子调用、goal 轮次共同核算；局部只能收紧 |
| call_depth | 8 | 可配置上限；动态等待图另行检测死锁 |
| recovery | 无自动业务返工；不盲目重放不明结果 | 安全技术重试、显式返工路由、暂停和恢复 |
| supervision | 关闭 | 观察周期、真实进展指标、诊断 Agent 和可执行动作 |
| knowledge | 无共享知识 | 显式只读来源、版本化可写知识；冲突返回，不自动覆盖 |
| service stop | 停止接收新请求，排空已接纳请求 | 立即取消模式；每个请求仍受原期限限制 |
| config update | 新版本用于新请求，活动调用保持原版本 | 显式暂停、切换和恢复；不改写历史输入 |

这些字段必须真实影响行为。不得用“暂未实现但接受配置”满足可配置要求。拒绝未知字段、重复键、任意 YAML 对象构造和任意可执行表达式。

未在表内确定的纯技术参数由实现者选取明确默认值，并与测试、Wiki 同步；不得借此削减上述能力或增加业务审批门槛。

### 3.3 引用、协作与生命周期

- 标准成员：agent.output、agent.artifacts.name、agent.status、agent.progress、agent.tags。SDK 自动管理状态与身份，用户仅声明业务输出。
- 隐式名称只在当前任务链、问题和轮次内解析；多个实例匹配时报歧义，禁止取全局“最新结果”。文件字符串与引用通过类型或显式 ref 区分。
- 下游绑定已提交输出的具体版本；必需输入未到齐不启动，上游失败不等于空输入。重复投递不重复创建业务调用。
- 动态 fan-out 使用 SDK 返回的调用组；显式关闭组后，全部必需结果齐备才触发汇总。
- SDK 提供受控 call-and-wait 与 send 工具。可以生成预声明角色实例，不能通过工具参数伪造调用者、预算、会话或执行身份。
- 静态依赖环在校验时报错；显式返工创建新轮次。动态等待环及同会话递归等待返回明确错误，不占住锁无限等待。
- 异步发送默认仍属于原请求链，不因发送而获得独立预算；独立任务由宿主显式提交。
- 每个外部根请求建立独立 AgentRun，并映射到独立的现有 SDK Run ID；嵌套 Agent 调用继承该请求链。服务元数据具有独立持久服务 ID，不借用第一个请求的 Run 身份、权限或预算。跨 Run 验收必须核对两个不同底层 SDK Run ID，分别保留期限、用量和取消范围。
- 等待子调用时可让出调度执行名额，但仍存活的父运行时保留内存预留，直到其资源确实释放。内存准入按声明预留求和，不根据瞬时 RSS 猜测释放，也不把预留值当作物理内存峰值上限。
- goal 验证失败反馈同一会话；普通 reviewer 拒绝不会自动拉起作者，只有显式规则或授权工具调用才触发返工。
- 服务身份、收件箱和会话映射跨 Run 保存；空闲时可释放进程。不同会话隔离历史及私有目录；同键恢复时须匹配当前配置版本，版本变化建立明确的新会话代次，不静默混合提示词或权限。
- 共享知识通过显式工具读取版本和提交更新，首版历史版本保留，不自动 GC。服务寿命、会话历史和请求执行权限分别管理。
- 用户停止、权限撤销和预算耗尽持久保存，宿主重启不自动解除。取消只作用于准确的调用及所属子调用，不影响无关会话。

### 3.4 文件权限保证

- 默认 tools 模式只保证 SDK 文件工具按声明检查路径及真实目标；额外 shell、MCP 或其他工具单独配置，不宣传进程级隔离。
- 文件工具在实际打开/修改时使用平台支持的根目录约束与句柄校验，避免“检查路径后被替换”的绕过；不能落实所声明路径保证的操作失败关闭并报告平台限制。路径预检单独通过不构成访问授权。
- strict 为宿主隔离能力合同：只有绑定能实际落实声明的后端才能启动，否则在业务执行前明确失败；不得静默降级。
- 首版必须交付 strict 能力协商、拒绝路径及适配器合同，不要求新开发一套通用操作系统沙箱。若宣称某个 strict 后端已支持，必须提供该后端的真实逃逸负例与允许操作正例；模拟后端不能证明隔离。
- 没有宣称支持的真实 strict 后端时，G13 的 passed 仅表示能力合同与拒绝路径通过；报告和 Wiki 必须同时写明“原生强隔离后端未提供、真实隔离未验收”，不得据此宣称 strict 执行可用。
- 输出归档、SDK 私有状态和模型凭据位于模型不能通过 SDK 文件工具任意写入的宿主目录。声明权限不自动授权读取宿主凭据。

## 4. 持久化与故障合同

新增版本化 Agent 控制存储，保存配置、会话、收件箱、调用映射与产物引用。Kernel/Orchestrator 保留执行、预算和结算权威；通过公共接口集成，不另建绕过底层保护的调度器。

跨存储按以下顺序恢复：先保存稳定意图 ID，再提交 SDK，结果不明则查询原回执；结果经持久收件箱消费，在同一控制存储事务保存消费标记与下一步提交意图。明确跨存储非原子，不承诺任意外部效果恰好一次。

配置版本与会话归属受独占租约和代次保护。OpenCode 请求已发但结果不明时先查询原会话；无法判断时保持 recovery_required/unknown，不默认再执行一次。取消请求、权限撤销、进程退出、清理确认和业务终态分别保留证据。

控制存储从 schema 1 开始；现有 SDK 存储变化只有必要时引入，并交付显式升级、失败恢复和回归。不得自动迁移用户库。会话历史或配置缺失不得伪造为可恢复。

## 5. 实施顺序

1. **P1 契约**：字段注册表、类型、解析、默认值展开、权限校验、错误定位和初版 Wiki。
2. **P2 最小真实执行**：安装包中的 AgentApp 实际启动 OpenCode，执行、调用文件工具、交付产物、取消。
3. **P3 协作**：依赖触发、动态实例、调用工具、汇总、调用授权及死锁检测。
4. **P4 持续运行**：goal、会话续接、跨 Run 服务、知识、配置版本与前台宿主。
5. **P5 故障恢复**：提交边界崩溃、租约竞争、预算连续性、取消传播和未知清理。
6. **P6 验收交付**：独立审查、隔离安装包、原生矩阵、双语 Wiki、示例、证据清单。

每阶段先完成最小真实路径再扩大测试。复杂架构、公共 API、持久化和并发改动按适用 AGENTS.md 使用独立审查；修复后验证。所有已知缺陷修复后才运行或触发 CI。通过且未受后续变更影响的验证无需无故重复。

## 6. 证据格式与验证入口

实施时新增 `scripts/verify_agent_control.py`，支持 `--list`、`--case ID`、`--layer unit|integration|native|all`、`--output DIR`。该入口不触发远程 CI，也不自行构建或替换被测包。

验证器必须能在源码目录外，从全新环境安装的 wheel 导入公共 API；native 层运行真实 OpenCode，并保存实际解释器、模块路径、包版本、OpenCode 版本、测试配置和执行结果。不得用 PYTHONPATH 指向 checkout 来冒充安装包。

运行报告 `acceptance.json` 按验收 ID 记录：status、场景、layer、平台/架构/Python、包路径与版本、配置版本、命令、退出码、开始/结束时间、原始证据路径和限制。status 只使用 passed、failed、blocked、not_run、not_applicable。初始全部 not_run；未知不是 passed。

证据文件使用独立目录；仓库内 `docs/SDK_0_8_0_AGENT_CONTROL_ACCEPTANCE.md` 保存索引、可复现命令和结论。对外文档不得依赖仅在本机存在的证据才能解释 API。

模型凭据由现有授权的宿主配置提供，不打印、不写入证据。没有可用配置时先完成不依赖凭据的工作，将 native 项标记 blocked，说明最小解除条件，不能替换为假模型后宣布完成。

## 7. 必须通过的验收矩阵

| ID | 可验证结果 | 最低证据要求 |
| --- | --- | --- |
| G01 | YAML/Python 配置等价；默认值展开准确；未知字段、重复键及非法覆盖拒绝 | 公共 API 测试、有效配置输出；字段注册表与 Wiki 对照 |
| G02 | 新环境安装 wheel 后，AgentApp 实际启动 OpenCode 并完成模型调用 | 实际导入来源、OpenCode 进程与会话、真实模型返回、SDK 结果；禁止仅健康检查 |
| G03 | 文件工具允许声明路径、拒绝越界和符号链接/路径替换逃逸；命名产物可由下游实际读取 | 原生工具调用、路径替换竞争负例、原始拒绝与真实文件内容；不支持的操作失败关闭并说明平台范围 |
| G04 | 输入未齐不启动；齐备后启动一次；重复事件不重复调度；同 ID 不同内容冲突 | 两个生产者、消费者实际执行；重复及冲突负例 |
| G05 | planner → 至少两个 coder → reviewer → 显式返工 → 原 reviewer 消费新结果 | 真 OpenCode 与 SDK 调用链、准确输入/产物绑定、reviewer 实际消费反馈 |
| G06 | 动态实例、关闭调用组和汇总可用；不同任务/轮次不串结果 | 并发正例、歧义引用/未关闭组/缺失输入负例 |
| G07 | call-and-wait、send、允许调用和禁止调用均有效；等待环不会挂死 | 实际 SDK 工具入口、调用者归属、原始失败、有限时间内返回 |
| G08 | response 和 goal 可用；验证失败继续原会话，明确阻塞可退出；验证器错误不算成功 | 验证先失败后通过的真实会话、阻塞与异常负例 |
| G09 | 同键续接、不同键隔离、同会话 FIFO、队列满及替换策略有效 | 至少两个会话和两个并发调用者；消息与结果逐项对应 |
| G10 | 同一服务跨两个不同底层 SDK Run 工作，保留各自预算和取消范围；客户端退出后仍可接收；宿主重启后续接并保留队列 | 独立 serve 进程、两个 SDK Run ID、独立请求预算、客户端退出记录、宿主真实重启、原服务和会话映射 |
| G11 | 配置更新不改变活动执行；新请求使用新版本；共享知识无授权不能写、版本冲突不覆盖 | 两个配置版本与知识版本、实际读取和拒绝记录 |
| G12 | 技术失败、业务拒绝、返工和不明效果被正确区分；不盲目重放 | 故障注入、执行次数和效果记录；原失败保留 |
| G13 | strict 能力声明有效：不支持时业务前拒绝，已支持后端兑现保证 | 缺能力负例；每个宣称支持的真实后端必须有允许/越界正反例；无真实后端不得声称强隔离已验收 |
| G14 | 意图提交、SDK 提交后回执前、模型请求后、消费结果后等崩溃窗口可恢复或准确报告 unknown | 真实进程故障/重启；原操作 ID、回执和下一步调用核对；无重复副作用宣称 |

平台要求：保留现有 Python 3.10–3.13、Linux/Windows、x64/ARM 适用矩阵；Windows ARM Python 3.10 沿用现有明确记录的 x64 兼容范围。2026-11-16 交付目标更正为 Linux x86_64。真实 OpenCode 验收沿用该平台候选包的已有证据；本轮 GitHub CI 只运行 Linux x86_64 的 Python 3.10–3.13 作业。其他平台的验证、完整安装包回归和正式发布仍按各自证据记录。保留既有有依据的平台不适用项；新增缺环境、凭据、权限、测试超时或功能未实现均不能改标 not_applicable。

远程 CI 未获授权时可使用已授权原生主机收集同等范围证据；若仍缺平台，G18 保持 blocked，报告已完成工作与具体缺项。不得为宣称完成而缩减支持范围。

## 8. 完成判定、阻塞与最终交付

完成必须同时满足：

1. G01–G18 均通过适用要求；条件性后端范围按 G13 明确，不冒充真实隔离支持。
2. 没有未修复的已知范围内缺陷或独立审查阻塞项。
3. 用户仅使用文档中的 YAML、公开 Python API 或 CLI 就能复现最小调用与协作示例，不需要私有函数、手写 SQL 或借用 ModPort 运行副本。
4. 代码、安装包、默认值注册表、中英文 Wiki 和验收报告对应同一最终候选；后续变更按影响范围重验。
5. 保留范围边界：SDK 完成不表示 ModPort 接入、旧 Run 恢复或 Minecraft 业务验收完成。

不得以待办清单、计划、mock 通过、进程活着或中间阶段成功标记 Goal complete。遇到外部阻塞时继续完成独立工作，记录尝试、原始证据、未满足的验收 ID 和最小解除条件。遵循当前 Goal 工具的阻塞状态规则，不通过改写本合同或降低测试标准消除阻塞。

最终交付：本地分支、实现与公共类型、可运行示例、验证入口、验收索引与证据、中英文 Wiki 源文件及导出预览、独立审查结论。最终报告分别列出实现、安装包、真实 OpenCode、故障恢复、平台覆盖、文档和远程发布状态。
