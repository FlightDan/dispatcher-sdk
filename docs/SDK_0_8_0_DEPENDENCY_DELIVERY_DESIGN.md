# Agent 依赖结果投递：实施草案

状态：部分实现、未验收。本文按 Goal 第 4 节和 G04 设计 SDK 内部的持久结果投递；它不宣称接收外部消息或消费现有 Orchestrator 通知队列。当前宿主已接入事件计划的投递，升级前已有计划仍按扫描模式推进；候选 48 的重复观察不能证明重复投递。

G04 要求重复事件，但没有指定外部消息源；本草案选择 SDK 内部持久生产者事实作为待验证的事件边界。验收时必须明确标记此边界，不能将本地投递描述为外部消息投递；它是否满足整项验收仍须结合真实执行证据审查。

## 边界

- 普通调用由 Orchestrator 任务承载，协调调用由 Kernel 子执行承载。本设计在两者归一到 Agent 控制存储的终态事实处生成事件，不冒充任一路径的底层通知。
- 事件仅表示对应 Agent 控制事实及其来源，SDK 执行、预算、效果和结算仍以现有公开接口为权威。SDK 结果与控制存储不能跨库原子提交；提交前后必须按原身份重新查询并对账。
- 本地取消、预算失败、直接创建的失败节点和 `recovery_required` 也可能成为依赖来源。没有真实 SDK 执行身份时不得伪造；`recovery_required` 保持现有上游失败处理，不能转换为成功数据。
- 终态不只由 `AgentStore.finish` 写入：计划节点可直接以终态插入，应用、服务收件箱和任务实例也有与队列或所有者状态同事务的终态写入。实现前必须逐一清点并在原事务内统一事件创建，不能事后另开事务补写而丢失故障窗口。
- 成功产物先按现有接口提交并保留版本，再将不可变终态和对应版本引用与事件放在同一控制存储事务中。事务不能声称与 SDK 结果或外部效果原子。

## 数据与升级

计划使用新的控制存储 schema 版本，保存事件、面向计划的接收与消费状态，以及明确的投递代次和确认信息。稳定事件 UUID 在首次终态事务内生成并持久保存；接收身份由该 ID 与目标计划作用域组成，投递租约及代次与事件身份分开。重复使用同 ID 且内容不同必须冲突。事件内容记录原 Run、根调用、生产者、轮次、真实存在的执行身份、代次和产物版本；本地事实明确标识来源，不能填充虚构身份。内容按可比较的规范编码保存，不新增摘要校验。

版本 1 存储只能通过持有宿主独占锁的显式停机升级转换；在宿主初始化写入前检查，单事务校验完整旧结构、创建新结构并更新版本，失败回滚，不触碰 SDK 数据库。新空存储采用新版本；旧活动计划的历史事实如需回填，必须标记为恢复来源并与已创建节点对账，不能伪称曾经投递。如选择继续扫描旧计划，须持久记录其兼容标记和结束条件。具体策略及崩溃、重开、损坏结构测试尚待完成，并须与独立版本化的服务 schema 升级协调。

当前实现为全部已有计划保存 `legacy_scan` 模式及冻结文档原文；已关闭计划的模式同时标记结束。新计划与 `event` 模式、冻结文档在同一控制事务创建，关闭时同步结束模式。检查时两份冻结文档必须一致，不能把缺失标记的已有计划当成新计划，也不根据现存结果补造旧事件。旧计划无任务代次字段的既有形式仍予保留。宿主已启用这些标记和钩子；旧计划升级后的实际 SDK 执行和完整嵌套配置兼容仍需验证，不能把原语测试视为完整升级验收。

## 接收与推进

1. 任何目标开始消费之前，必须根据冻结计划持久化完整的（事件、计划、目标角色）作用域集合。优先在生产者终态事务中同时保存事件及全部作用域；若异步枚举，则必须持久记录未完成状态，在同一事务写完全部作用域并标记完成，重开后继续，完成前拒绝消费。接收端核对事件 ID、完整内容、作用域和实际生产者事实；重复接收相同内容返回原接收记录，不同内容返回冲突。没有目标的事件也要有明确结算。
2. 每个目标后继使用独立的投递作用域（计划与目标角色），在同一控制存储事务读取计划、精确生产者事实和产物版本，计算该后继是否就绪；同时写入该作用域的接收／消费标记与新后继的稳定意图和绑定。输入未齐时可消费事件但不能提交后继。这样，一个目标的邮箱拒绝不会回滚其他目标已提交的意图；不同目标各自保留待重试的投递状态。各事务重新读取当前完整候选集合，不使用早先快照掩盖新出现的作用域歧义。
3. 事务提交后才提交或对账现有 SDK 命令；提交结果不明时查询相同意图的 SDK 回执，不创建第二个执行。已存在的计划节点仍使用根调用、轮次和 plan_key 的唯一约束与内容冲突检查。
4. 确认丢失时必须把同一事件再次送到真实接收事务，证明接收两次但后继只创建一次。不同执行代次或不同产物版本不得合并。保留事实扫描作为恢复兜底，两条路径共用事务化计划决策以避免竞态；验收必须让第二生产者事件实际创建消费者意图，再丢失确认并重投同一事件，而非扫描已提前完成后仅重放无关记录。
5. 宿主关闭时拒绝新投递，等待已进入的接收和提交尾部；超时保留准确所有者及未完成状态。过期投递所有者不能确认新代次。已关闭或取消计划的事件需记录明确的无操作结算；毒事件、冲突和未知效果须可观察并阻止错误成功，重开后恢复准确待处理记录。

首次消费在同一个写事务中读取收据、验证事件和源事实，再规划目标并保存其准确结果和消费标记；目标直接进入终态时也必须记录其身份。已消费事件重投时读取原结果，不再次运行规划器。宿主以单调时钟、宿主代次和每次领取的独立凭据隔离旧租约：必须先持有独占锁、提交新的宿主代次并在整个代次期间保持锁，同一代次的租约操作必须由同一宿主进程执行。不得在领取事务提交前对外发布凭据。租约授权在事务内操作时判断；写锁负责串行化该事务和后续领取，事务中不得执行外部副作用，事务提交时间本身不承诺早于租约截止时间。系统休眠期间单调时钟的行为依平台而定。

当前关闭与已进入的投递通过应用锁串行；期限到达而投递仍未退出时保留宿主所有权。关闭不保证所有尚未领取的接收记录已处理；这些记录留在控制存储中，由下一宿主在独占锁下换代后恢复。前台 drain 完成图计划也不等于每个已关闭计划的接收记录均已确认。消费后但尚未成功提交的后继意图须由宿主独立对账；投递确认不是 SDK 执行成功的证明。

## 必要验证

- 两种执行路径分别覆盖：第一生产者完成但输入未齐；第二生产者完成；同一事件接收两次；冲突内容拒绝；消费者只创建一个 SDK 执行并绑定两个准确生产者，产物引用另核对各自版本。
- 在事件提交前后、消费与意图事务前后、SDK 提交及回执确认前后注入中断；重开原状态并验证稳定身份、原期限和未知效果。
- 用隔离安装包、真实 OpenCode 双生产者及消费者重复上述实际投递，记录事件 ID、两次投递、消费事务、绑定、SDK 执行和最终确认。合成适配器只用于故障覆盖，不能代替真实模型验收。
- 显式升级覆盖旧状态保留、独占锁、异常回滚、部分或未知 schema 拒绝；不修改用户原有 SDK 存储。
