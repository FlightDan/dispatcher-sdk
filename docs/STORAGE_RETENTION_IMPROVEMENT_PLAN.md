## 1. 问题与证据

ModPort 的需求来源为其 `docs/SDK_STORAGE_RETENTION_PROPOSAL.md` 和
`docs/validation/2026-09-16-run-retention.md`。其中约 134.6 GB 数据库及冷归档的状态是上游记录，本次未重新验证归档。

SDK 侧已确认的写入路径：

- `orchestrator/engine.py::apply_operations` 将显式提交的 `application_state` 放入完整 request，并保存为 `application.decided`。
- `orchestrator/store.py::_save` 只跳过与当前 item 完全相同的值；`application_state` 内一个小字段变化，也会保存整项 JSON。
- `_write_receipt` 已使用紧凑 revision 引用；`_receipt` 依赖 `_load_at` 重建原始响应，因此回执仍会间接固定历史数据。
- `continue_run` 保留前序数据，在同库创建新 Run；它不压缩、不回收，也不自动继承完整当前状态。
- `storage.py` 已有只读兼容性预检、单库一致备份和 SQL 导出，没有完整保留、容量、维护和归档协议。

本次临时库复现：每种场景 80 次独立提交，状态含相同的 512 KiB 字符串，Kernel 使用独立数据库。

| 场景 | Orchestrator 主库字节数 | 主要原因 |
| --- | ---: | --- |
| 每次显式提交相同状态 | 43,270,144 | 决策事件重复保存大状态 |
| 每次仅修改一个计数器 | 84,738,048 | 决策事件与历史共同重复保存大状态 |
| 首次之后省略状态参数 | 1,806,336 | 后续事件不再携带大状态 |

这不是对任意业务负载的容量预测。已有 history/preflight 测试 14/14 通过，但未覆盖上述增长场景。

## 2. 目标与不可破坏的约束

1. 大值物理增长主要取决于不同内容总量；revision、事件及引用元数据仍允许随操作数线性增长。
2. 存储编码与应用值分离：升级和去重不能改变 `get_run`、`get_run_at`、事件、回执和重放返回的逻辑值、类型、身份或顺序。
3. 请求指纹和既有审计哈希继续基于原有逻辑内容；不得改成压缩字节或物理对象引用的哈希。
4. 默认不自动删历史、不缩短幂等保证、不清理审计证据。保留策略必须显式启用。
5. 历史保留窗口不是删除授权：当前状态、回执、恢复、未完成投递、来源认证等保护根优先，报告必须解释未能回收的原因。
6. 升级、归档、恢复、替换文件等操作均有空间预检、维护隔离、可恢复进度和发布边界；普通打开不得触发大规模迁移。
7. SDK 管理自己的存储与已登记对象；未登记的业务文件不扫描删除，任意 JSON 中的路径不自动当作所有权或引用声明。
8. 停止进程不等于 Run terminal。业务状态、实际执行状态、维护状态分别检查。

兼容性的边界：物理升级必须保持全部原语义；用户另行启用历史过期策略后，历史读取或旧事件 cursor 可以返回明确的“已过期”结果。这是显式保留契约，不可伪装成未知 Run、空列表或成功重放。当前 Run 快照及受保护回执不受此例外影响。

## 3. 存储模型

### 3.1 首先采用同库内容寻址对象

首期把对象放在 Orchestrator SQLite 文件内，利用同一事务提交对象、引用、历史、事件和回执，避免过早引入文件系统与 SQLite 的双重提交。

候选结构：

- `sdk_content_objects`：对象格式版本、摘要、编码、逻辑长度、存储长度、内容。
- 持久化值的显式编码标记：区分旧版 inline JSON 与新版结构树；内部引用不得与用户字典中的特殊键混淆。
- `sdk_content_refs`：拥有记录及其字段路径到对象的边，用于可达性分析；它是可验证索引，不是唯一事实来源。
- 存储身份与变化序号：稳定 store ID、incarnation、维护 epoch，以及覆盖非 Run revision 写入的 mutation sequence。
- 保留时间元数据：P1 为受支持的新格式记录明确的创建/提交与确认/完成时间，按类别定义年龄起点；由所属组件在原写入事务内持久化。使用受控 UTC 时钟并记录时钟异常，不以文件 mtime 或 ID 推算时间；时钟不可信时拒绝年龄删除，仍可使用数量策略。旧记录缺失值显式标记 unknown。
- 持久序列高水位：事件、outbox 等每个序列空间保留历史已分配上界，即使记录全部删除也不能回退；它属于逻辑存储状态及变化 token。

编码规则：

1. 对 `application_state` 使用递归结构编码，将达到阈值的大字符串或大子树转为对象引用；初始阈值建议 64 KiB，可配置。
2. 大父对象以小结构节点引用子对象，避免“整个 application_state 做一次哈希”导致计数器变化仍复制稳定大字段。数组保留顺序与元素身份语义；首期不承诺任意文本编辑的分块去重。
3. 当前值、历史和事件共享同一 codec 和对象表；recovery 表中直接保存的 application state/decision 也纳入写入路径审计与编码。
4. 摘要基于有版本及类型域的确定性逻辑编码。装载时验证摘要、长度和结构；缺失、损坏、解压超限时停止返回数据。
5. 可选压缩在去重之后进行，压缩收益不作为去重正确性的证据；设置解压大小和递归深度限制。
6. 逻辑指纹在替换为物理引用之前计算。API 返回时透明还原，不向现有消费者泄露内部引用。

首期去重范围保证同一 Run 内历史与事件共享；同库允许跨 Run 复用，但所有权、引用和删除按共享对象处理。跨数据库复用后置。

### 3.2 历史重建与回执

历史是增量记录。保留 revision R 时，必须保留每个字段在 R 之前最近的有效值，或生成等价检查点；不能只按 revision 下限删除行。

命令回执默认永久可重放：

- 保留命令身份、请求摘要及原始逻辑响应的可解析引用。
- 初期继续固定对应历史，优先保证兼容；只做内容去重，可能无法回收大量历史元数据。
- 后续可把回执依赖转换为独立、去重的不可变响应检查点，或认证的冷存响应。转换前后重放结果必须相等。
- 不提供“删除幂等记录后把同一 command ID 当新命令”的默认行为。若未来提供幂等窗口，必须另设明确契约和过期身份拒绝机制。

当前 `get_run()` 包含完整 attempts。即使策略只保留最近 N 个 terminal attempts，也不能直接删掉当前快照中的旧 attempts：首版将这些记录标为受保护；后续允许冷存并透明补齐，或通过另行版本化的 API 契约改变读取模型。

## 4. 只读容量与可达性分析

新增独立 API，复用只读连接基础，不通过 `Orchestrator(...)` 初始化 writer：

- `inspect_storage_usage(scope, detail=...)`：快速物理统计与可选深度逻辑统计。
- `plan_retention(scope, policy)`：生成删除候选、保护原因、对象闭包及容量估算。

报告至少区分：

- 主库分配页、空闲页、索引、WAL/journal、SHM、外部对象、备份和操作临时空间。
- 表/载荷类别的逻辑字节与实际存储字节；共享对象只在总量中计一次，按 Run 的共享分摊另列，不能误加。
- 可删除逻辑字节、删除后页内空闲、预计压缩后文件大小；估计值附方法、范围和不确定性。
- 保护根、跨 Run 引用、不可解析引用、认证失败、扫描是否完整、扫描预算与续扫位置。

快速检查不隐式执行全库 `quick_check` 或全量 JSON 解码。深度扫描可分批输出大型删除清单，清单带内容摘要和稳定身份；不得把百万行计划全部加载到内存。

只读保证：不初始化 SDK writer、不升级、不生成备份、不隐式 checkpoint。SQLite WAL 读取所需共享内存条件不满足时返回明确诊断；不能用 `immutable=1` 忽略可能存在的 WAL。严格不允许创建 sidecar 的环境必须先验证读取条件。

多库在线计划注明各自 snapshot token，不能声称是原子跨库视图。真正执行前在统一维护隔离下重新核对所有 token；不一致则要求重算。

计划绑定 policy digest、store ID/incarnation、schema/codec 版本、mutation sequence、维护 epoch、来源注册表版本、对象清单摘要及失效条件。Run revision 单独不足以检测 outbox ack、lease 和 recovery 写入。

## 5. 保留策略、prune 与对象 GC

`RetentionPolicy` 独立配置 policy revisions、terminal attempts、决策/唤醒事件、opaque state 历史、已确认 outbox、已完成 Effects 等类别的数量或时间窗口；默认均不删除。

可达性根至少包括：

- 当前快照与保留 revision 的重建闭包；
- 命令回执、幂等身份、执行 provenance、continuation；
- 活跃与待确认的 recovery、Effects、投递、结果、notification 和 event subscriptions；
- 不可删除审计证据、不可变输入、认证冷归档 locator；
- 正在发布的 snapshot、迁移、恢复及尚未提交的对象引用。

时间策略需要可靠的记录时间。旧数据缺少相应时间时不得推测；仅支持数量策略或报告该项不可执行。事件 sequence 不重编号；过期 cursor 显式报错并提供可用水位，不能静默跳过。

提交时间、完成时间和 ack 时间不能混用。P0 固化各类别时钟及年龄起点，P1 在受支持组件的新格式中同步落地；未升级时间元数据的 Kernel/inbox 等组件不得宣称支持对应年龄策略。升级、压缩、备份及恢复必须复制独立序列高水位，不能用存活记录的 `MAX(sequence)` 重建。

已完成 Effect 的幂等记录不因“completed”自动可删；必须证明没有可重放或恢复路径，或保留紧凑永久身份记录。已确认 outbox 同样检查所有消费者及恢复依赖。

执行采用 `apply_retention(plan, lease)`：

1. 验证计划摘要、租约、身份及全部变化 token。
2. 同一 SQLite 事务内重验候选及引用闭包，只删除未受保护记录，登记操作回执；事务失败保持原逻辑数据。
3. 单库可保证原子删除；跨库采用可恢复的阶段协议，先持久化保留引用与发布标记，再清理旧数据。失败时允许多留数据，不允许少留引用。
4. 返回实际删除数、保护数、空间变化和操作 ID。重复调用同一操作 ID 返回既有结果。

外部对象 GC 后置于对象所有权登记：标记 → 隔离/待删 → 持久化引用重验 → unlink。它与对象发布共享维护隔离或 epoch 保护，不能仅凭一次 refcount=0 unlink；外部写入必须先持久化对象再提交引用，失败可留下可识别孤儿。

## 6. 维护隔离、压缩和发布

### 6.1 统一维护协调器

新增 store-group 级协调器，包含公开 lease ID、owner、用途、到期时间、fence 和参与组件。协调信息和锁必须位于不会随业务数据库替换的稳定位置。

P0 定义 `StoreGroupDescriptor`/handle：包含 group ID、稳定协调器入口、成员 store ID 与组件身份、当前 generation 及格式版本。跨目录/多盘组件通过显式 handle 加入同一 group；路径本身不代表成员身份。新单库部署可在创建时生成默认 descriptor，既有多库部署通过显式注册/升级绑定。

每个组件的持久元数据绑定 group ID 和 store ID，opener 在任何 writer 初始化前解析 descriptor、验证成员和 generation、加入协调器。只传路径的现有构造形式通过已登记绑定解析；缺失、冲突或失效绑定不得回退到独立 writer。复制文件不会自动成为可写的新成员。涉及 Kernel/inbox/journal 新元数据时必须分别升级其 schema，并通过版本拒绝及部署停写阻断旧 writer 混跑。

- 覆盖所有 SDK writer：Orchestrator、Kernel、inbox、sandbox journal、recovery、GC 和归档注册表。
- 普通读写持有参与锁；需要稳定 inode 的读取覆盖整个读取生命周期。维护者取得独占锁后拒绝新参与者，并等待已有参与者安全退出。
- 活跃 worker/外部 Effect 必须完成明确 quiesce 握手；不能只检查数据库连接已关闭。
- 每次写入提交路径验证有效身份与 fence。租约到期不构成绕过仍被持有的物理锁的授权；旧持有者不能在新 epoch 发布。
- 拒绝过期、外来或作用域不足的租约；公开 blockers，不根据进程名或锁文件存在与否推断安全。
- 旧版 writer 不遵循新协议，必须停止并通过显式部署切换排除；维护协议不能保证绕过 SDK 的任意 SQL writer 安全。

该 lease 与 reopen 专用 recovery lease 分离。Linux/Windows 分别验证锁和发布实现；文件系统能力不足时拒绝相应操作。

### 6.2 压缩与文件替换

prune 提交与物理压缩是独立阶段。默认 prune 只产生可复用页，不承诺立刻缩小主库文件。

压缩流程：空间预检 → 独占维护隔离 → 创建后继数据库 → 检查 schema/对象/逻辑等价性及完整性 → flush → 发布 → 验证重开 → 标记完成。

保留已验证的原文件或恢复副本直到发布完成。中断恢复根据操作 manifest 确认哪一代有效；不能自动打开混合代数据。

单库同文件系统可使用经平台验证的原子替换。多库不能逐个 rename 后宣称原子：使用不可变 generation 目录和一个原子切换的 manifest/pointer，所有 SDK opener 先解析该入口。固定旧路径入口的迁移必须显式完成。跨文件系统先复制到目标同文件系统的 staging 再发布。

## 7. 一致快照、恢复与 compact successor

为 store group 登记完整组件清单：Orchestrator、Kernel、inbox、audit、sandbox/recovery journal、不可变输入、外部 blobs，以及共享所有权关系。

`snapshot_run` 在 quiesce 下创建认证 manifest，覆盖每个组件的身份、schema、逻辑水位、文件摘要、对象引用、来源和所需部署绑定。SQLite 通过一致备份纳入已提交 WAL 内容，不以复制 live 主文件替代。

`restore_snapshot` 先在 staging 校验全套数据、路径边界、签名/摘要、组件匹配和对象完整性，然后通过 generation 发布。任意组件缺失或来源不匹配时拒绝发布。

首版只允许恢复到独立空目标及新 incarnation，默认以隔离只读状态发布，不覆盖已经接受更新的现有 store。转为可执行状态前必须排除原身份仍在执行并完成 group/来源绑定，避免两个副本重复工作。发布使用期望 generation/incarnation/epoch 的 compare-and-swap；目标变化或出现快照后的已接受写入时拒绝覆盖。就地回滚不在首版范围内，不能以“完整旧快照”替代新命令回执和幂等证据。

认证区分完整性摘要与可信来源：提供签名/验证接口和 trust policy；签名密钥由部署方管理，SDK 不内置固定秘密。算法、key ID、manifest 格式可版本化，缺少可信验证材料时不得声称来源已认证。

`compact_successor` 创建新 Run identity，携带当前逻辑应用状态、任务来源映射、必要证据与恢复约束，但不复制全部旧 revision：

- 原 Run 继续保留可解析来源，原回执仍归原身份，不能把旧 command ID 在新 Run 中重放为新工作。
- 未完成 execution、Effect、投递或 recovery 的转移需要独立所有权迁移协议。首版只接受无此类未解决义务的已静止源；否则返回 blockers，不能直接复制租约或隐式重新执行。
- 当前状态中的旧 attempts/证据可以通过认证冷引用保留逻辑读取能力，必须验证新旧读取及来源映射的一致性。
- 该操作本身不自动删除源数据，空间回收需要独立归档/保留计划。

这不能保证立即接续 ModPort 的 v17：其持久化 Run 仍为 running，是否具备安全的 successor 前置条件需要在可验证源数据上检查。

## 8. 跨 Run 来源登记、归档与 disposal

注册表使用稳定 store ID + Run ID + 来源摘要标识，记录引用边、所有权、hot location、认证 archive locator 和注册表版本。仅同名 Run ID 不足以认证来源。

业务侧通过显式扩展接口登记 SDK 无法理解的引用。提供完整性声明；来源范围不完整、跨组引用无法核对或摘要不匹配时，计划失败关闭，不能据此永久删除。

归档顺序：生成不可变包与 manifest → 验证完整性及来源 → 发布可解析 cold locator → 再释放 hot 副本。注册表变更与新引用创建需要统一序列化/墓碑检查，消除“检查后又新增引用”的竞争。

`plan_disposal` / `dispose_run` 支持 dry-run、archive-first 和明确的永久删除模式：

- 要求业务 terminal、无活跃执行、无未解决恢复/投递/Effect，以及完整可验证的引用范围。
- 被 continuation/recovery 等引用的 Run 默认拒绝永久删除；可归档并保留来源解析。archive-first 不等于解除引用保护。
- 列出全部拥有记录、文件和共享对象；共享数据库只能删除本 Run 可删除记录，不能删除整个文件。
- 采用幂等操作日志及 deleting 状态，中断后可恢复；源清理完成后发布小型签名 tombstone。签名准备失败不得先删源。
- tombstone 保留身份、源 manifest 摘要、操作 ID、时间、策略及归档 locator；它不能替代仍受保护的任务证据。

回执契约按模式明确区分：archive-first 保留冷存响应解析和原幂等保证；永久 disposal 是调用者显式选择的整 Run 读取/重放终止，不沿用“永久可重放”的承诺。永久 tombstone 和身份注册表禁止该 Run 身份重新创建；旧命令重试、`get_command_receipt` 及其他读取统一返回明确 `RunDisposed`，不能返回 None、伪造旧响应或执行为新命令。永久删除只在全部引用保护条件满足后允许，原身份封禁记录不随载荷删除。

## 9. 配额与遥测

配额按 store group 的实际物理资源管理，另提供 Run 逻辑用量。共享对象归属、跨 Run 分摊与总物理量分别展示。

- soft limit：每次跨越仅产生一个可行动告警；回落采用明确恢复阈值，避免告警风暴。事件内容小且可去重。
- hard limit：写入前保守预留对象、索引、页增长和 WAL 上界；并发写共享预留账本，不能各自对旧用量检查后同时超额。
- 预算包括备份、归档、压缩输出、恢复 artifact 和临时峰值；分别检查各目标文件系统可用空间。
- 预估不足时事务回滚，不提交部分 revision。SQLite page 限额只能作为一层保护，不能代表 WAL/多库/外部文件总限额。
- 设置纳入总预算的应急额度，供取消、ack、恢复和维护日志推进，避免满额后无法收敛。
- 对无可靠增长上界的操作，严格模式拒绝执行，而不是宣称已满足硬限制。外部非 SDK writer 的空间增长只能检测，无法由 SDK 强制约束。

公开 current/reserved/projected/peak、各组件用量、去重节省、受保护字节和阻塞原因。遥测自身有有界存储策略。

## 10. 显式升级与存量大库治理

### 10.1 格式升级

采用新的 Orchestrator schema/codec 版本；最终版本号实现时分配。Kernel 不因 Orchestrator 去重自动改版本，只有实际修改其持久化格式时才升级。

普通打开：识别旧版并返回明确升级要求，不建对象表、不启动转换。

升级工具：

1. 只读识别 schema、组件、身份、部署绑定和空间需求。
2. 获取完整维护隔离，记录源指纹；创建独立目标代与可恢复操作 manifest。
3. 分批读取、确定性编码、复用对象；支持中断续跑，但每次恢复先确认源未变。
4. 核对行数/身份、逻辑摘要、历史重建、事件、回执、recovery、独立序列高水位和审计哈希。
5. 验证目标后发布新代；保留原代直到明确完成验证及备份保留条件。

升级与保留分开执行：升级阶段不顺手删除历史。发布失败回到原代；新代一旦接受新写入，不可简单切回旧代丢弃这些写入，必须停止并执行前向恢复或另行的数据迁移。

### 10.2 ModPort 旧大库

1. 对冷归档重新校验 manifest、文件摘要、来源身份及 fail-closed marker 状态；历史 header mismatch 保留为 blocker。
2. 优先在容量足够的 HDD/scratch 区处理，明确解压后源、目标、备份、WAL 和临时文件的峰值，避免再次占满工作盘。
3. 普通压缩 SQLite 归档不能假定可随机读取当前状态。没有独立认证的当前快照时，通常仍需在 scratch 恢复可读源；空间不够就报告阻塞，不能承诺无完整恢复提取。
4. 对源进行只读使用量、来源及恢复义务分析，选择完整去重升级，或满足前置条件后创建 compact successor。
5. 在 staging 验证 ModPort 的逻辑状态、任务来源及恢复要求。其已有应用层 blob 引用需由适配器登记/认证/还原，SDK 不能把任意业务字典自动当内部引用。
6. 发布新 hot location 后保留已验证旧冷归档，按独立策略决定是否回收；不通过改写历史 input 修复身份不匹配。

## 11. 分阶段交付与依赖

| 阶段 | 交付内容 | 进入下一阶段的门槛 |
| --- | --- | --- |
| P0 证据与契约 | 固化复现脚本；API/写入路径清单；codec、回执、历史过期、时钟及 group 绑定契约；只读容量 MVP | 可重现增长并给出有边界的容量报告 |
| P1 新写入去重 | 同库对象及递归 codec；history/event/recovery 集成；时间元数据与序列高水位；分组件新格式与旧库拒绝提示 | 增长、透明读取、重放、损坏和事务原子性测试通过 |
| P2 安全维护与显式升级 | 协调器、全写入路径 fence、稳定读者登记、操作 manifest、空间预检及 copy-upgrade | 中断/租约/并发与跨平台发布验证通过 |
| P3 保留和单库压缩 | 完整可达性计划、回执保护、历史基线、单库 prune、同库对象 GC、压缩 | 无受保护数据丢失，陈旧计划拒绝，故障后可重开 |
| P4 快照与来源 | store-group manifest、签名与信任接口、注册表、归档、restore、受限 compact successor | 跨库一致性、cold locator 解析、来源异常阻断通过 |
| P5 完整生命周期 | 外部对象发布/GC、Run disposal、完整配额强制、遥测与大库迁移演练 | 全部生命周期验收及真实规模空间/耗时记录完成 |

依赖主线为 P0 → P1 → P2 → P3 → P4 → P5。P0 容量统计和 P1 codec 可以在接口确定后并行；配额记账字段从 P1 开始设计，完整强制能力在 P5 验收。P3 首版只处理引用范围完整的同库数据；跨库/外部引用不明时拒绝清理，等待 P4/P5。

P1 可先服务新库；旧生产库必须等 P2 显式升级。对旧库不得把 P1 当作可直接部署的热修复。

建议模块边界：保留 `storage.py` 现有 API，内部按 codec/objects、usage、reachability、maintenance、migration、snapshot、provenance、quota 拆分；不要把所有生命周期逻辑塞入 `StoreMixin`。新增公开 API 在实现阶段纳入 `PUBLIC_API.md`，本方案不宣称其已可调用。

## 12. 验收与发布条件

### 12.1 功能与容量

- 稳定 512 KiB 大值重复 10,000 次：分别测试状态完全相同、仅小字段变化、A/B/A 复用、嵌套数组、不同 Run、不同内容。
- 使用确定性高熵数据并提供关闭压缩组；检查唯一对象数及对象载荷总量，不能靠重复字符压缩掩盖未去重。
- 对 100/1,000/10,000 次提交记录主库、WAL、逻辑内容、对象和引用元数据增长；物理预算按唯一内容与有界每次提交元数据制定。
- 原始值、事件、历史快照、命令回执和重放结果与旧模型逐项相等；请求摘要和审计哈希不变。
- 删除历史后保留 revision 的基线完整；当前 attempts、未完成 Effects、未 ack 投递、continuation/recovery 均不丢失。
- 删除全部或尾部事件/outbox 后，升级、压缩及恢复仍保留其高水位；再次写入的 sequence 大于该序列空间历史最大值，旧 cursor 显式过期。
- archive-first 后原回执仍可解析；永久 disposal 后所有旧命令与同 Run 身份重建均返回 `RunDisposed`，不发生重复执行。
- 分别记录 prune 后空闲页与 compact 后物理空间。发布前基于 SQLite 版本、页大小和负载测量并公布估算误差；不预先承诺固定百分比。

### 12.2 并发与故障

- 计划期间插入 revision、ack outbox、更新 recovery/registry、发布对象后，旧计划均被拒绝或重新完整验证。
- live writer、稳定 inode reader、未静止 worker、过期/外来 lease、租约接管后旧 owner 提交均被拒绝。
- 迁移、压缩、快照、恢复、注册表更新、GC、disposal 的每个持久化/发布边界注入失败并重启。
- 任何中断只暴露旧完整代或新完整代；跨组件绝不混代。GC/disposal 失败最多留下可追踪冗余数据。
- 目标已有快照后新写入、generation 竞争变化或原执行身份仍活跃时，restore 拒绝覆盖或激活；恢复不能丢失已接受命令或产生双活副本。
- 磁盘满、quota 并发预留、WAL 增长和压缩双份空间不足时，不产生部分逻辑 revision。
- 缺失对象、摘要不符、超大解压、非法路径、symlink、坏签名和来源 header mismatch 失败关闭。

### 12.3 验证方式与范围

- 每阶段执行相关单元、集成及故障测试；持久化/并发变更独立审查后再最终验证。
- 10,000 次增长和大库迁移放独立慢测试/演练，常规 CI 使用缩小但能检测相同缺陷的样本。
- Linux 和 Windows 均测试实际锁、文件替换、fsync 能力边界及重新打开；不以 CI 配置代替已通过记录。
- SDK 先使用合成大库和复制件演练；真实 ModPort 归档只有在单独授权执行治理、预检通过后才操作。
- 为每阶段记录源码版本、schema、平台、测试命令、结果、容量与耗时、已知限制。不得将本方案或此前 14 个通过测试描述为新能力已经完成。

## 13. 最终交付清单

- 向后保持逻辑读取语义的去重存储与显式升级工具。
- 只读 usage/reachability 报告、可核验保留计划及幂等维护操作结果。
- 已认证的 snapshot/restore、来源注册表和有明确前置条件的 compact successor。
- 带所有权检查的外部对象 GC、归档和 terminal-Run disposal。
- 含并发预留与临时峰值的配额、可行动遥测和阻塞诊断。
- API 文档、升级/恢复手册、业务 blob 适配说明、容量基准、故障与跨平台验证记录。

优先完成 P0/P1 来阻止新写入继续放大；P2/P3 提供安全存量转换与回收基础；P4/P5 才补齐跨库、冷归档和完整生命周期治理。
